# VMDU（Unicode 版 VMD）構想メモ

更新日: 2026-08-04
状態: 構想 / 未実装

## このメモの役割

VMD の文字コード制約を取り除いた拡張形式「VMDU」（仮称）の方針をまとめる。実装仕様書ではなく、方向と範囲を決めるための設計メモである。

現時点で着手しない。VMD 出力の実装が先である（理由は「順序」節）。

## 動機

VMD はボーン名・表情名・モデル名を Shift-JIS の固定長フィールドで持つ。このため次の問題がある。

- 中国圏でも MMD は人気があるが、向こうの漢字はほぼ文字化けする状態で無理やり本家 MMD を使っているとのこと。
- 日本語圏以外のモデル、長いカスタムボーン名を持つモデルで、名前が切り詰められる、あるいは表現できない。

一方 PMX は 2.0 でエンコーディングフラグを持ち、UTF-16LE / UTF-8 を選べる。**モデル側は既に Unicode 対応済みであり、連鎖の中で VMD だけがレガシーとして残っている。**

VMDU は新しい表現力を足す形式ではなく、**最後に残った1つの穴を塞ぐ形式**として位置づける。

## 結論（現時点の方針）

1. 文字コードは **UTF-8 一本**。BOM なし。エンコーディングフラグを設けない。
2. **VMD → VMDU は機械的にコンバートできる**ように作る。
3. **逆変換（VMDU → VMD）は用意しない。** Unicode 文字列を Shift-JIS の VMD に詰めることは原理的にできない。
4. 代わりに、**アプリから VMD 書き出しを選べる**ようにする。
5. 構造は VMD を踏襲する。意味論を追加しない。

### 「変換」ではなく「書き出し」にする理由

変換を用意すると2形式が等価であるという印象になり、失敗したときにバグに見える。書き出しなら、制約のある的に向けて狭める操作だと理解される。

実務上も、アプリのほうが情報を持っている。PMX が読み込まれているため、名前が実在するボーンを指しているか、切り詰めたとき衝突するかを判断できる。ファイル単体の変換器にはその文脈がない。**変換は文脈のある場所に置く。**

### エンコーディングフラグを設けない理由

PMX は UTF-16LE と UTF-8 を選べるため、実装者は両方を書く必要がある。選べる自由は規格にとって負債になる。適合実装を増やすには1つに固定するほうがよい。

## スコープ

### 対象

- 文字列フィールドの文字コードと長さ制約

### 対象外（調査により除外）

**キーフレーム数の上限は VMD 形式の側に存在しない。**

有志による VMD 解析メモによれば、キーフレーム数の上限（32bit 版で 300,000、64bit 版 7.39dot 以降で 600,000）は MMD 側が設けている制限である。形式上は各セクションのキー数が DWORD で持たれており、約42億まで表現できる。フレーム番号も DWORD である。

したがって VMDU で拡張すべき上限は存在しない。**当初「文字コードと上限」の2点としていたスコープは、文字コードのみに縮小する。**

MMD_modoki 側は 300,000 という制限を持つ必要がない。VMD 書き出し時に「本家では読めない可能性がある」と警告する形が正しい対応になる。

なお上限判定ではフレーム0のキー（既定でモデルのボーン数と同数）もカウントされる点に注意する。

## 未決定事項

### 文字列フィールドを固定長のままにするか、可変長にするか

**案A: 固定長のままバイト数を増やす**

- レコード長が計算で求まる。オフセット計算でのシーク、メモリマップ、非確保パースが可能
- VMD → VMDU がほぼバイトコピーで済む
- バイト数を決める必要がある。決め方は、手元の PMX を走査してボーン名・表情名の UTF-8 バイト長のヒストグラムを取り、最大値に余裕を掛ける
- UTF-8 では CJK が3バイトになるため、Shift-JIS 時代より入る文字数が減る。15バイトのままでは悪化する
- 切り詰めロジックが残る

**案B: PMX の仕様に寄せて可変長にする**

- PMX と同じ「int32 長さ + バイト列」になり、PMX パーサを持つ実装者がコードを流用できる
- バイト数を決めなくてよい。「なぜ64バイトか」を説明しなくてよい
- 切り詰めロジックが不要になる
- 短い名前は短いまま格納されるため、案Aより小さくなる可能性が高い
- セクションを読み飛ばせなくなる。→ **ヘッダに各セクションのバイト長を持たせれば回復できる**。これは将来「知らないセクションを長さで飛ばす」拡張性にも効く

どちらを選ぶにせよ、実装者は Shift-JIS → UTF-8 の処理を新規に書くことになるため、固定長を維持することによる利得は当初想定より小さい。

### その他

- 固定長を選ぶ場合のバイト数
- 正規化形の指定（比較は NFC 正規化後に行う、等）。macOS が NFD を生成するため、クロスプラットフォームでは無視できない
- どのセクションまでを必須とするか（VMD は MMD のバージョンによって照明まで / セルフ影まで / 表示IK までと終端が異なる）
- 拡張子とマジックヘッダの具体値

## やらないこと

- **意味論の追加。** 新しいキー種別、新しいチャンネル、新しい機能を入れない。VMD でできることを、制限なくできるようにするだけに留める。
- **名前テーブル + インデックス参照。** ファイルは小さくなるが、二回走査、インデックス検証、範囲外エラーという新しい壊れ方が増える。将来ファイルサイズが問題になったら v2 で検討する。そのために**バージョンフィールドは最初から入れる**。
- **評価セマンティクスの仕様策定。** MMD の付与親・IK・補間・評価順といった振る舞いの仕様化は、VMDU とは別件である。あの領域の知見は babylon-mmd をはじめとする既存実装の解析成果に多くを負っており、単独で標準として公開する筋の話ではない。VMDU はバイト配置の話に留める。
- **VMD と間違われる形にしない。** 拡張子とマジックヘッダを VMD と明確に分ける。誤って読ませたとき、静かに変な結果を出すのではなく、はっきり失敗する。

## 順序

**VMD 出力の実装が先。これは妥協ではなく要件収集である。**

15バイトで実際に何が溢れるのか、どのような衝突が起きるのか、どのフィールドの精度が足りないのかは、VMD の読み書きを書いてみないと出てこない。実装経験なしに厳密な仕様は書けない。

VMDU は何のクリティカルパスにも乗っていない。アプリから VMD 書き出しができれば配布は成立する。VMDU は純粋に加算的であり、後からいつ足してもよい。

## 策定の姿勢

他所のアプリも読む形式になりうるため、成果物は実装ではなく**仕様書**になる。

VMD には公式仕様が存在せず、有志の解析だけで20年運用されてきた。そのため実装ごとに解釈が異なる余地が残っている。VMDU がそれを繰り返さないために、次を用意する。

- コードを読まずに実装できる文書（バイト配置、フィールド長、エンコーディング、エラー時の扱い）
- **適合テストデータ。** エッジケースを含むサンプルファイル一式。これがないと各実装が推測し、静かに分裂する
- バージョンフィールドと、未知バージョンを読んだときの挙動の規定

厳密にするのは仕様の書き方であって、機能範囲ではない。**範囲はケチにする。**規格にしようとすると「うちのこれも入れて」が来るが、そこで膨らむと誰も実装しない規格になる。

### 検証

VMD の制限内に収まるデータであれば、次が成り立つはずである。

```other
VMD → VMDU → VMD がバイト一致する
```

製品機能としての逆変換は用意しないが、**検証目的の降格経路をテスト内に持てば**この性質を自動テストにできる。既存の VMD をそのまま入力に使えるため、テストデータに困らない。
