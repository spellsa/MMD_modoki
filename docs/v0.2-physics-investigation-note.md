# v0.2 物理演算・高負荷モデル調査メモ

更新日: 2026-04-27

## 目的

v0.2 では、Babylon.js 9.2.0 + babylon-mmd 1.2.0 を前提に、重めモデルでも扱いやすい物理演算へ寄せる。

このメモでは、v0.2 で調査・実装判断する物理まわりと高負荷 MMD モデル対応の項目を整理する。実装手順の詳細は既存の [physics-worker-implementation-plan.md](./physics-worker-implementation-plan.md) を参照する。

基本方針として、物理、マルチスレッド、GPU skinning / SDEF、高ポリゴンモデル読み込みは babylon-mmd の推奨する実装経路を素直に採用する。
MMD_modoki 側に残っている旧バージョン向けの回避コードや独自調整は、v0.2 の更新では維持を前提にしない。
必要なものだけを新しい経路へ移植し、古い実装は破棄してよい。
MMD_modoki 側で新たに足す責務は、主に Electron / Vite / packaged build 上で babylon-mmd の推奨経路が動くようにする統合部分とする。

## 優先順位

1. `MmdWasmInstanceTypeMPR` / Worker 物理の導入可否
2. `PhysicsRuntimeEvaluationType.Buffered` の採用可否
3. GPU skinning / SDEF / 多ポリゴンモデル読み込みの推奨経路確認
4. MPR 失敗時の SPR fallback
5. 重めモデル / 複数モデルでの FPS と physics time 比較
6. seek / Home / End / 再生開始 / ボーン編集後の安定性
7. 物理 backend 表示と performance log

## 現行前提

- 現在は babylon-mmd の Bullet WASM 物理を主経路にしている。
- Bullet 失敗時は Ammo.js へ fallback する。
- 物理 ON / OFF、重力、fixed step、substep は既に扱っている。
- `disableOffsetForConstraintFrame: true` は維持する。
- v0.2 で babylon-mmd は `1.2.0`、Babylon.js は `9.2.0` に更新済み。

ただし、これらの現行実装は v0.1 系向けに作った安定化コードを含む。
v0.2 では、現行コードの延命より babylon-mmd 1.2.0 の推奨経路へ寄せることを優先する。

## 採用条件

MPR / Buffered / GPU skinning 推奨経路を v0.2 標準候補にする条件:

- WebGPU 起動と同時に安定して初期化できる
- packaged build でも Worker / WASM / shader asset の解決が壊れない
- MPR 失敗時に SPR または Ammo へ自然に fallback できる
- SDEF / GPU skinning が babylon-mmd 推奨経路で動く
- 重めモデルで FPS または UI 応答性に明確な改善がある
- seek / pause / resume / Home / End 後に破綻しない
- 物理 OFF / backend 切替時に既存プロジェクトの読み込みを壊さない

見送り条件:

- COOP / COEP 対応が既存のローカルファイル読み込みを壊す
- Worker / WASM / shader asset の packaged build 解決が不安定
- Buffered で操作後の姿勢同期が目立って遅れる
- babylon-mmd 推奨経路から外れた独自実装が増えすぎる
- SPR と比べて改善が小さい一方で、実装・保守コストが大きい

## 実装方針メモ

- 最初は設定画面や詳細 UI へ広げず、内部切替 + debug 表示で検証する。
- babylon-mmd 1.2.0 の推奨実装を第一候補にし、v0.1 系向けの古い回避コードは必要なら破棄する。
- MMD_modoki 側の実装は Electron / Vite / packaged build 統合と、UI 表示・ログ・fallback に寄せる。
- MPR を入れても SPR を消さない。SPR は fallback と比較基準として残す。
- Ammo fallback は互換退避経路として残すが、v0.2 の主評価対象は Bullet SPR / Bullet MPR にする。
- 現行の Bullet / Ammo 初期化コードを流用する場合も、推奨経路との差分が説明できる範囲に留める。
- GPU skinning / SDEF は babylon-mmd 側の機能を使い、独自 shader 差し込みはできるだけ減らす。
- 通常再生と編集操作では最適な評価モードが違う可能性があるため、最初から固定せず比較する。
- 物理 performance log は SQLite 実験とは混ぜず、まずメモリ内集計または console/debug 表示に留める。

## 実装プラン

### Phase 1: 現行差分の整理

対象:

- `src/mmd-manager.ts`
- `src/assets/model-asset-service.ts`

確認する現行差分:

- 現在は `spr` wasm を直接 import し、独自の `loadSprWasmInstance()` 経由で初期化している
- backend 表示は `bullet | ammo | none` で、SPR / MPR の区別がない
- `SdefInjector.OverrideEngineCreateEffect(engine)` は既に呼んでいる
- WebGPU SDEF mesh を CPU skinning に落とす独自 fallback が残っている
- 高ボーン数 skeleton を CPU skinning に落とす独自 fallback がある

方針:

- babylon-mmd 1.2.0 推奨の `GetMmdWasmInstance(new MmdWasmInstanceTypeMPR())` / `MultiPhysicsRuntime` / `MmdBulletPhysics` を基準にする
- v0.1 系向けの回避コードは、推奨経路と衝突する場合は破棄する
- GPU / Electron 制約のために必要な fallback は、理由を明確にして残す

### Phase 2: backend 種別の細分化

`physicsBackend` を次の粒度へ変更する:

```ts
"none" | "bullet-spr" | "bullet-mpr" | "ammo"
```

対応する表示:

- `Bullet MPR`
- `Bullet SPR`
- `Ammo`
- `Off`

更新対象:

- backend badge
- `getPhysicsBackendLabel()`
- smoke log
- diagnostics / console log
- fallback warning

fallback 経路は `MPR -> SPR -> Ammo -> none` として記録する。

### Phase 3: MPR 初期化を主経路にする

初期化順:

1. MPR 利用可否を判定する
   - `SharedArrayBuffer`
   - `crossOriginIsolated`
   - COOP / COEP
   - Worker helper / WASM asset の URL 解決
2. MPR 初期化を試す
3. MPR 失敗時は SPR へ fallback
4. SPR 失敗時は Ammo へ fallback
5. Ammo 失敗時は physics off

`MultiPhysicsRuntime` は MPR / SPR の共通経路として使い、MMD runtime 側には `MmdBulletPhysics(runtime)` を接続する。

MMD_modoki 側では、Worker や WASM の中身を再実装しない。必要なのは Electron / Vite / packaged build で babylon-mmd の推奨経路が成立するようにする統合部分に限定する。

実装時の補足:

- MPR は `GetMmdWasmInstance(new MmdWasmInstanceTypeMPR())` を主経路にする
- SPR は Vite / Electron dev 環境で babylon-mmd 標準の URL 解決が HTML に落ちるケースがあるため、当面は明示的に `spr/index_bg.wasm?url` を渡す fallback 経路を維持する
- SPR の明示 URL 経路は、babylon-mmd の wasm / typed array API を使う統合コードとして扱い、Worker / 物理実装そのものは再実装しない

### Phase 4: Buffered 評価の段階導入

MPR 起動が安定してから、`PhysicsRuntimeEvaluationType.Buffered` を試す。

初期方針:

- 通常再生: Buffered 候補
- seek / Home / End 直後: Immediate 候補
- ボーンギズモ操作中・直後: Immediate 候補
- pause 中の手動編集: Immediate 候補

Buffered は性能改善が出ても、操作直後の姿勢同期が悪ければ標準にしない。

### Phase 5: CPU fallback の棚卸し

`applyCpuSkinningFallbackForWebGpuSdefMeshes()` は Babylon 8 時代の WebGPU / SDEF 回避実装の可能性がある。
v0.2 では、babylon-mmd 1.2.0 + Babylon.js 9.2.0 の推奨 SDEF / WGSL 経路で再確認し、不要なら削除候補にする。

一方、高ボーン数で GPU bone texture の上限を超える fallback は、Babylon / GPU 制約への退避として残す可能性がある。

分類:

- 推奨経路と衝突する旧回避コード: 破棄候補
- GPU / Electron / packaged build 制約の退避: 条件付きで維持
- 原因が不明なまま残っている fallback: 調査して削除または明文化

### Phase 6: 計測

最初は大きな UI を作らず、console / diagnostics / 簡易 debug 表示で確認する。

測るもの:

- engine: WebGPU / WebGL2
- backend: Bullet MPR / Bullet SPR / Ammo / Off
- evaluation: Immediate / Buffered
- model count
- FPS
- physics step time
- fallback reason
- CPU skinning fallback の有無

### 最初の実装単位

最初の差分は、物理初期化と表示に閉じる。

1. `physicsBackend` を `bullet-spr` / `bullet-mpr` に細分化する
2. MPR 可否判定 helper を追加する
3. MPR 初期化を主経路に追加する
4. MPR 失敗時 SPR fallback を実装する
5. UI / log / smoke の backend 表示を更新する
6. WebGPU SDEF CPU fallback を feature flag 的に切れる形へ変更する
7. `npm.cmd run lint`
8. `npm.cmd run smoke:launch`

Buffered 評価と CPU fallback 削除は、MPR 起動確認後に別差分で扱う。

### 2026-04-27 WebGPU SDEF CPU fallback の扱い

実装方針:

- Babylon.js 9.2.0 + babylon-mmd 1.2.0 では、まず babylon-mmd 側の SDEF / WGSL 経路を優先する
- v0.1 系の WebGPU SDEF CPU fallback は既定で無効化し、必要な場合だけ戻せる実験フラグにする
- 高ボーン数 skeleton の CPU fallback は Babylon.js 9 の 2D bone matrix texture 経路と衝突するため削除する

実装済み:

- `applyCpuSkinningFallbackForWebGpuSdefMeshes()` は `mmd_modoki.webGpuSdefCpuFallback` が有効な場合だけ実行する
- 既定値は `false`
- 必要な場合は DevTools 等から `localStorage.setItem("mmd_modoki.webGpuSdefCpuFallback", "1")` で旧 fallback を有効化できる
- import 前の高ボーン数 CPU skinning fallback observer を削除した
- import 後の oversized skeleton CPU skinning fallback を削除した
- `(bones + 1) * 4 > maxTextureSize` の場合は、Babylon.js 9 の 2D bone matrix texture に任せる
- 高ボーン数 skeleton では `GPU bone texture: ...` diagnostic を残す

次に確認すること:

- 4274 ボーン級モデルで `Early CPU skinning fallback armed before import` が出ないこと
- 同モデルで `GPU bone texture: ...` が出て GPU skinning が維持されること
- SDEF / position morph を含むモデルで WebGPU 表示が破綻しないか確認する
- 破綻するモデルがある場合だけ、fallback 条件をモデル単位または mesh 単位で再設計する
- 問題が出なければ、この fallback は削除候補にする

確認結果:

- 4274 ボーン級モデルで `Early CPU skinning fallback armed before import` は出なくなった
- 同モデルで `GPU bone texture storage enabled for large skeleton` が出た
- bone matrix texture は `8192x3` として確保された
- CPU fallback 時に出ていたモーフによる顔崩れが改善した
- 動画出力でも物理演算は動作した
- FPS は CPU fallback 時も GPU bone texture 時も 1fps 程度で、対象モデルが重すぎるため性能差は判断不能
- 中規模モデル 4 体のプロジェクトでは、体感で 5〜10fps 程度の改善が見えた

- COEP 付与後に PMX texture、音声、ローカル隣接ファイル解決が壊れないか、実データで確認する
- 現時点の package 版は `MPR packaged build integration is pending` として SPR fallback する設計にしている

### 2026-04-27 Buffered 評価の初期導入

実装済み:

- babylon-mmd の `PhysicsRuntimeEvaluationType` を使い、`MultiPhysicsRuntime.evaluationType` を切り替える経路を追加した
- MPR + 通常再生 + 物理有効時に `Buffered` へ切り替える実験を行った
- 実モデル複数体の再生中に、物理剛体がボーンへ追従せず髪や剛体付きパーツが崩れる現象が出た
- 2026-04-27 時点では再生中も `Immediate` 固定へ戻した
- 10 秒ごとの物理ログに `evaluationType` を含める

方針:

- Buffered は物理を別 worker 側へ逃がせる可能性がある一方、seek や手動編集では 1 フレーム遅れや同期ズレが見えやすい
- 現時点では、MMD_modoki の複数モデル再生 / 手動 seek / 既存の `afterPhysics` patch と衝突している可能性が高い
- v0.2 初期実装では `Immediate` を標準にし、Buffered は別途検証が終わるまで標準経路に入れない
- SPR fallback と package 版では、現時点では Immediate 中心で扱う

確認結果:

- `npm.cmd run lint`: 成功。既存 warning のみ
- `npm.cmd run smoke:launch`: 成功。`engine=WebGPU`, `physics=Bullet MPR`, `crossOriginIsolated=true`

次に確認すること:

### 2026-04-28 `MmdWasmRuntime` 切り替え式 PoC

実装方針:

- 既定は従来の `MmdRuntime` + Bullet MPR のままにする
- `localStorage["mmd_modoki.runtimeMode"] === "wasm"` のときだけ、実験的に `MmdWasmRuntime` + `MmdWasmPhysics` を使う
- ツールバー右側の `Runtime` select から `Classic` / `WASM` を切り替えられるようにする。変更後は runtime 再初期化のため自動で再読み込みする
- WASM runtime 初期化に失敗した場合は warning を残し、従来 runtime / physics 初期化へ fallback する
- モデル用 VMD / VPD animation は、WASM mode では `MmdWasmAnimation` で包んでから runtime animation を作成する
- WASM mode では従来 runtime 向けの bone evaluation order 補正と paused physics patch は適用しない
- UI の physics badge では `WASM MPR` として区別する

切り替え方法:

- 通常はツールバー右側の `Runtime` select で `WASM` を選ぶ
- コンソールから切り替える場合:

```js
localStorage.setItem("mmd_modoki.runtimeMode", "wasm");
// 戻す場合
localStorage.setItem("mmd_modoki.runtimeMode", "classic");
```

確認済み:

- `npm.cmd run lint`: 成功。既存 warning のみ
- `npm.cmd run smoke:launch`: 従来 classic mode で成功。`engine=WebGPU`, `physics=Bullet MPR`, `crossOriginIsolated=true`

## 2026-06-29 追記: 長髪モデルの物理伸び

`GirlsFrontline ClukayDefault` で、停止中は正常に見える髪が、物理演算ありの再生中にゆっくり伸びるように破綻する症状を確認した。

スクリーンショット: `スクリーンショット 2026-06-29 122256.png`

現時点では実装変更せず、診断対象として記録する。見た目の材質問題ではなく、物理剛体 / joint / ボーン同期 / step 制御の問題である可能性が高い。

疑わしい原因:

- 再生開始時やフレームシーク後に物理状態が十分 reset されていない。
- 物理 step の delta time、substep、`maxStepNum` が長髪 joint chain に対して大きい。
- 剛体初期姿勢とボーン初期姿勢の同期がズレており、再生時に物理剛体へ切り替わると髪が引っ張られる。
- `disableBidirectionalTransformation` / `disableOffsetForConstraintFrame` 相当の挙動、または mode 2 の bone alignment が MMD と一致していない。
- joint の linear limit / angular limit / spring 値の解釈差。
- モデルスケールと physics world scale のズレ。
