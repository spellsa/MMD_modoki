# 作業0: ボトルネックの切り分け計測

## 背景

2026-04-22 時点の実測は draw 十数ms / capture 90ms 前後 / encode 1ms 前後で、capture の内訳は `mapAsync` 待ちが支配的とされている。

ただし 1920x1080 RGBA8 は 8.3MB であり、転送量としては本来 1ms 未満で運べる量である。90ms を転送時間で説明することはできない。

また `mapAsync` は、対象バッファに関わるコマンドがすべて完了するまで解決しない。したがって **draw のコマンドを積んだ直後に `mapAsync` を待つ構造だと、GPU のレンダリング時間そのものが capture に計上される。** 現状の draw 計測値が「submit までの CPU 時間」であれば、SSAO / SSR / Bloom などの実際の GPU 実行時間はどこにも現れず、すべて capture の中にいることになる。

過去にパイプライン化（staging バッファのリング化）を試して改善しなかった、という経緯もこの仮説と整合する。GPU が律速なら並列化しても縮まない。

## 実施内容

### 0-1. 空シーンでの計測

既存の性能ログ（`docs/performance-logging-guide-2026-06-15.md` の仕組み）をそのまま使う。**新規に計測コードを書かない。**

条件:

- モデルなし、アクセサリなし
- ポストエフェクトを全て OFF（Bloom / DoF / Luminous / SSAO / SSR / Offset Rim / Offset Shadow / Vignette / Grain / Sharpen / Chroma / Edge blur / Distort）
- **解像度・フレーム数は過去の計測と同一にする**（変えると比較にならない）
- 100 フレーム程度の WebM 書き出しを実行

記録する値: draw / capture / encode の内訳、および1フレームあたりの合計。

### 0-2. 判定

| capture の値  | 解釈                        | 次                    |
| ----------- | ------------------------- | -------------------- |
| 数 ms まで落ちる  | GPU 律速。90ms の主犯はレンダリングだった | 作業1以降を実施しない。 報告して止まる |
| 90ms 付近のまま  | 転送または CPU 側処理が主犯          | 作業1へ進む               |
| 中間（30〜50ms） | 両方寄与                      | 作業1へ進んでよいが、期待値を下げる   |

### 0-3. 現在の色変換の所在を確認

**コードを読んで、RGBA から YUV への変換が現状どこで行われているかを特定する。**

- MediaBunny / VideoEncoder に RGBA のまま渡している
- CPU（JS）側で I420 に変換してから渡している
- その他

**CPU 側で変換しているなら、作業1の効果は大きい。** 渡す前に変換が無いなら、作業1は「転送量を減らす」効果だけになる。

### 0-4. 追加計測（0-2 が GPU 律速だった場合のみ）

ポストエフェクトを1つずつ ON に戻し、どれが重いかの順位を出す。これは作業1とは別の改善テーマになる。

### 0-5. 報告

判定結果と実測値を報告して、いったん止まる。作業1へ進むかは人間が判断する。

**結果がどちらであっても、対象メモに `## Phase 0 実施結果 2026-08-xx` の節を追加して記録する。** GPU 律速だった場合は「主犯は readback ではなかった」という前提の訂正として残す。

# 作業1: RGBA → YUV(I420) の GPU 前処理

**作業0の判定が「作業1へ進む」だった場合のみ実施する。**

## 目的

`GPU -> CPU` に戻すデータ量を、RGBA 8.3MB/frame から I420 3.1MB/frame へ削減する（1920x1080 の場合、約 62% 減）。

encode 自体は既存の CPU 経路をそのまま使う。**VP8 のブロック処理・係数計算・bitstream 生成には一切踏み込まない。**

## 1-1. 出力フォーマットの仕様

I420（YUV 4:2:0 planar）。単一の storage buffer にタイトに詰める。

```other
offset 0                    : Y plane   w * h bytes
offset w*h                  : U plane   (w/2) * (h/2) bytes
offset w*h + (w/2)*(h/2)    : V plane   (w/2) * (h/2) bytes
合計 w * h * 3 / 2 bytes
```

各プレーンの stride はパディングなし（Y は w、U/V は w/2）。

## 1-2. 色変換の定義（最重要）

**ここを間違えると「なんとなく色が違う」という発見しにくいバグになる。実装前に定数を確定させ、コード中にコメントで規格名を明記すること。**

決めるべき項目:

1. **色空間**: BT.601 か BT.709 か。HD 解像度なら BT.709 が通常。**現行の出力が何を前提にしているかを先に確認する。** 現行経路と変えてはならない。
2. **レンジ**: limited range（Y: 16-235, UV: 16-240）か full range（0-255）か。
3. **入力のガンマ**: レンダーターゲットが sRGB エンコード済みか、リニアか。リニアのまま輝度を計算すると暗くなる。**現行経路と同じ状態の値を入力にすること。**

決めた内容は `VideoFrame` 生成時の `colorSpace`（`VideoColorSpace`）にも同じものを指定する。シェーダーと宣言がズレると再生側で色が変わる。

## 1-3. compute shader の構成

**1スレッドが 8x2 ピクセル領域を担当する構成を推奨する。**

理由: WGSL の storage buffer は 4 バイト単位のアクセスが基本であり、1バイトずつ書くのは扱いにくい。8x2 領域なら、

- Y: 16 サンプル = **4 回の u32 書き込み**（各行 8 サンプル = 2 u32、行内で連続）
- U: 4 サンプル = **1 回の u32 書き込み**
- V: 4 サンプル = **1 回の u32 書き込み**

となり、すべて 4 バイト境界に揃った書き込みだけで済む。

- workgroup_size は `(8, 8, 1)` 程度から始める。1 workgroup で 64x16 ピクセルを処理する。
- 実際の最適値は計測して決める。まず動かすことを優先する。

クロマのサブサンプリングは、2x2 の 4 ピクセルの U/V を平均する（単純平均でよい。box filter）。

### 解像度の制約

上記構成は幅が 8 の倍数、高さが 2 の倍数であることを前提とする。VP8 のマクロブロックは 16x16 なので、**出力解像度は 16 の倍数に丸めるのが最も安全**である。

丸めない場合は端のピクセルの扱いをシェーダー内で明示すること。**範囲外アクセスを silent に無視しない。**

## 1-4. パイプラインへの組み込み

現在の `GPUTexture -> GPUBuffer -> CPU RGBA -> VideoSample` を、次に置き換える。

```other
GPUTexture
  -> compute shader (RGBA -> I420)
  -> GPUBuffer (I420, 3/2 * w * h bytes)
  -> mapAsync
  -> Uint8Array
  -> new VideoFrame(data, { format: 'I420', ... })
  -> 既存の encode 経路
```

- 既存の `copyTextureToBuffer` 経路は**削除しない。** 実験フラグで切り替えられるようにし、既定は現行のままにする。
- compute shader の入力は、テクスチャを直接 `texture_2d<f32>` としてバインドする方式を推奨する（一度 buffer に落とさない）。

## 1-5. VideoFrame の生成

```other
new VideoFrame(uint8Array, {
  format: 'I420',
  codedWidth: w,
  codedHeight: h,
  timestamp: usec,
  layout: [
    { offset: 0,                     stride: w },
    { offset: w * h,                 stride: w / 2 },
    { offset: w * h + (w/2)*(h/2),   stride: w / 2 },
  ],
  colorSpace: { /* 1-2 で決めたもの */ },
});
```

**確認事項:** 現在の encode 経路（MediaBunny 側）が I420 の `VideoFrame` をそのまま受け取れるか。受け取れない場合は、受け取れる形式を確認してから進むこと。**推測で進めない。**

`frame.close()` を必ず呼ぶこと。

## 1-6. 検証

### 正しさ

CPU 側に同じ色変換のリファレンス実装（素朴な JS ループ）を書き、既知の RGBA パターン（グレースケール階調、原色、肌色、白飛び、黒潰れを含む）を両方に通して比較する。

- 判定は **各サンプルの絶対誤差の最大値**を出す形にする。丸め方の違いで ±1〜2 は出る。
- **ピクセル完全一致を合否条件にしない**（既存の Playwright 方針と同じ）。最大誤差を数値で報告する。
- この検証はレンダリングを必要としないため、Playwright 経由で Electron 上で実行できるはず。既存の E2E ハーネスに乗せられるか検討する。

### 見た目

同一シーン・同一フレーム範囲を、現行経路と新経路の両方で書き出し、並べて比較する。**色被り、彩度の違い、暗部の潰れ**を重点的に見る。これは手動チェックリスト行き。

### 速度

作業0と同じ条件で再計測し、draw / capture / encode の内訳を比較する。**capture 内を「copy + submit」と「mapAsync 待ち」に分けて記録する。**

## 1-7. やらないこと

- VP8 のブロック処理、動き予測、係数計算、エントロピー符号化、bitstream 生成
- VP9 への拡張
- 音声 mux の自前化
- **既存 MediaBunny 経路の削除**
- 既定経路の切り替え（実験フラグの裏に置く）
- 汎用の色変換ユーティリティ化（この用途専用でよい）

## 1-8. 撤退基準

作業1を実装した上で、**capture 時間が有意に改善しない場合は撤退する。**

その場合はシェーダーとフラグを削除し、対象メモに撤退理由と実測値を追記する。「データ量を 62% 減らしても改善しなかった」という事実自体が、Phase 2 以降に進まない根拠として価値がある。

## 1-9. 進め方

- 作業0と作業1はコミットを分ける。
- 作業1の中でも、シェーダー実装と検証、パイプライン組み込みでコミットを分けてよい。
- 1-2（色変換の定義）と 1-5（VideoFrame が I420 を受け取れるか）で確認が取れない場合は、実装を進めずその時点で報告して止まる。
