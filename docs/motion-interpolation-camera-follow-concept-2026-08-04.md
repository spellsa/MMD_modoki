# モーション補間・自動補完・カメラ追従の構想メモ

更新日: 2026-08-04
状態: 構想 / 未実装

## このメモの役割

モデルモーションとカメラモーションについて、次の機能をどのような責務と順序で実装するかを整理する。

- 既存キーの間を自然につなぐモーション補間
- キーが少ない区間を補う自動補完
- キャラクターの動きからカメラキーを生成する追従・ベイク
- 音量波形と拍列を使った音楽同期アシスト
- Babylon.js の汎用アニメーション機能を使う範囲
- MMD / VMD 固有の仕様として MMD_modoki 側で持つ範囲

これは実装仕様書ではなく、今後の実験と優先順位を決めるための設計メモである。

## 結論

現時点では、次の方針が妥当である。

1. 編集の正本は、VMD の意味を保持した MMD_modoki のモーションデータにする。
2. 補間・追従・IK 補正は、まずフレームごとの姿勢またはカメラ軌道として評価する。
3. 評価結果を必要に応じて通常のボーン / カメラキーへベイクする。
4. Babylon.js は、汎用補間、行列・クォータニオン計算、IK、プレビューに活用する。
5. MMD の補間曲線、PMX の階層、付与親、IK、物理、VMD 出力は MMD_modoki 側で管理する。
6. 「予測生成」や機械学習による長区間のモーション生成は、短区間の補間・接地補正が安定した後の Experimental とする。
7. 音楽同期では単一BPMを正本にせず、可変テンポにも対応できる編集可能なBeatMapを使う。

基本となる処理経路は次のとおり。

~~~text
元のモーション / カメラキー
        ↓
フレーム評価
        ↓
補間・追従・補正レイヤー
        ↓
IK / 接地 / 画角などの制約処理
        ↓
キー削減・補間曲線生成
        ↓
通常のモーションキーへベイク
        ↓
タイムライン編集 / VMD出力
~~~

プレビュー中は元データを変更せず、ベイク操作だけを Command として記録する。これにより、再計算・Undo / Redo・VMD出力の責務を分けられる。

## 用語の整理

### 補間

前後に存在するキーの間のフレームを評価すること。通常はキーを増やさなくても、再生時に値を求められる。

### 自動補完

指定区間に不足しているキーを生成すること。短いキー間の補間結果をキーとして保存する場合も含む。

### 予測生成

最後のキーより先の動き、または長い空白区間の動きを推定すること。入力情報が不足するため、補間とは別の Experimental 機能として扱う。

これらを同じ「自動補間」UIに混ぜると期待値が分かりにくくなるため、内部の処理とUI上の名前を分ける。

## モデルモーション

### まず実装する補正

MMDの基本編集体験として、次の順に扱う。

1. XYZ補正
   - 選択ボーンまたはセンターの移動量を X / Y / Z で一括適用する。
   - フレーム範囲を指定できるようにする。
   - 1回の補正を1つのUndo単位にする。
2. 既存キー間の補間
   - 位置は軸ごとに扱う。
   - 回転は最短経路を考慮したクォータニオン補間を基準にする。
   - MMD / VMD の補間曲線を保持できる場合は、その曲線を優先する。
3. 短い空白区間の自動補完
   - 前後キーと、その前後の速度・加速度を使う。
   - 補間結果を確認してからキーへベイクできるようにする。
4. 足接地・IK補正
   - 足先が接地している区間では足先のワールド位置を保つ。
   - 腰、センター、膝方向をIKで調整する。
   - 接地していない区間へ過剰に固定を伝播させない。

### 骨の種類ごとの扱い

| 対象 | 基本方針 |
| --- | --- |
| センター / ルート | 位置軌道、速度、接地、モデル体格差を優先する |
| 上半身 | 前後キーの回転補間と姿勢の連続性を優先する |
| 腕・脚 | 回転補間後に手先・足先のIK制約を適用する |
| 指 | まず単純補間。似たポーズ検索は後段で検討する |
| 物理連動ボーン | 原則として直接補完せず、制御ボーンから物理を再評価する |
| 表示 / IKプロパティ | 連続補間ではなくステップ値として扱う |

物理ボーンへ直接キーを生成すると、物理シミュレーションと手付けキーが競合しやすい。物理の焼き込みは、通常のモーション補完とは別の処理として設計する。

### 選択ボーンの床下貫通補正

床下へ埋まったボーンを補正する機能は、モデル全体を持ち上げる処理とは分ける。物理演算は補正対象・判定対象から外し、ユーザーが選択した通常ボーンだけを対象にする。

#### 単純床クランプ

移動可能なセンター、ルート、IKボーンなどは、選択ボーンのワールドYが床高さを下回った場合に、床までの差分だけ上へ移動する。

~~~text
correctionY = max(0, groundHeight - selectedBoneWorldY)
~~~

この補正は、まず「床下に埋まらない」ことだけを目的にする。姿勢全体の自然さや足滑りを同時に解こうとせず、現在の姿勢を保ったまま移動できるボーンを上へ逃がす。

#### 回転チェーン補正

肩・肘・手首、腰・膝・足首のように、対象ボーンの位置が親ボーンの回転で決まる場合は、対象ボーンだけをY移動しない。選択ボーンをエンドエフェクタとして、親チェーンをIKで解く。

~~~text
選択ボーンが床下
  → 親チェーンを取得
  → X/Zを保った床上の目標位置を作る
  → 親チェーンの回転を最小限変更して解く
  → 必要なら最近の移動可能親へ補正を逃がす
  → 補正結果を通常ボーンキーへベイク
~~~

補正の優先順位は次のとおり。

1. 選択ボーンを床上へ移動できるか確認する。
2. 移動可能ボーンなら、ワールドY差分を親ローカル移動へ変換する。
3. 回転専用ボーンなら、肩・肘・手首などの親チェーンをIKで調整する。
4. チェーンの可動範囲を超えた場合は、最近の移動可能親へ補正を分配する。
5. それでも解けない場合は、補正不足と最大回転量を診断へ残す。

回転チェーン補正では、元姿勢からの回転変化を最小化する。腕を床から逃がすために肘や肩が不自然な角度へ折れないよう、関節ごとの重み、最大回転量、優先軸を持たせる。

#### 物理の扱い

- 物理ボーンは補正対象に含めない。
- 物理計算結果で床下判定を行わない。
- プレビューでは物理を無視または停止した姿勢を基準にする。
- 通常ボーンへ補正キーをベイクした後の物理挙動は、別途再評価する。
- 物理ボーンへ直接キーを生成する「物理焼き込み」は、この機能とは別の処理にする。

#### 時間方向の連続性

各フレームを独立してIK解決すると、肘や肩が振動しやすい。次のフレームを解くときは前フレームの補正結果を初期値にし、回転差分を平滑化する。

- 前フレームの解を次フレームの初期値にする
- 最大回転速度を設ける
- 補正の入り・解除にスムージングを入れる
- 補正が必要なフレームだけキーを生成する
- ベイク前後で元姿勢との差分を表示できるようにする

#### 判定の段階

最初は選択ボーンの原点を床下判定に使う。後で必要になった場合に、次の順で精度を上げる。

1. ボーン原点
2. ボーンの線分または末端点
3. 足裏・手のひら・つま先などの接触プローブ
4. メッシュの局所的な最低点

モデル全体のバウンディングボックスだけを使うと、髪・スカート・アクセサリによって過剰に持ち上がる可能性があるため、通常の判定方法にはしない。

### 自動補完の候補アルゴリズム

#### 短い区間

短いキー間は、前後キーだけでなく隣接区間の速度を使った補間が候補になる。

- 位置: 線形、Hermite、minimum-jerk の比較
- 回転: Quaternion Slerp を基本に、必要なら接線を使った曲線
- 開始・停止: 速度を抑えた ease in / ease out
- 方向転換: 変曲点にキーを残し、過剰な丸めを避ける

単純な各ボーン独立補間だけでは、足滑り、膝の沈み、手先のずれが出やすい。そのため、補間の後に接地・IKなどの制約処理を置く。

#### 長い区間

前後キーだけでは情報が不足するため、次の候補を Experimental とする。

- 同じモーション内の似たポーズ区間を検索するモーションマッチング
- 既存の歩行・待機などのモーション断片を参照するモーションライブラリ
- 左右対称・反転ポーズを参照する補完
- センター移動、足接地、手先位置などの制約を満たす軌道探索

機械学習による生成は、参照モーションの品質、モデルごとの骨格差、再現性、配布サイズが課題になるため、最初の補間機能には含めない。

### 手動キーの優先

- 手動で編集したキーは自動補完で上書きしない。
- 自動生成キーと手動キーの境界を内部状態で区別できるようにする。
- VMDへ出力する際は、生成元のメタデータは必要に応じて破棄し、通常のVMDキーへ変換する。
- 補完結果が不自然な場合に、対象ボーン・区間・生成キー数を確認できるようにする。

最初の実装では、完全な非破壊レイヤーを作るより「プレビュー」と「ベイクを1 Commandで適用」の二段階で十分である。

## 音楽同期アシスト

ダンス動画を主な利用対象とするなら、音声解析は付加的な表示ではなく、モーション編集のタイミング基盤として扱う価値がある。ただし、MMD_modokiがDAWになることを目標にはしない。音声は編集対象というより、ボーン・カメラ・モーフを編集するためのリズム情報の入力とする。

### BPMではなく拍列を正本にする

曲全体のBPMだけでは、途中のテンポ変更、変拍子、ハーフタイム / ダブルタイム、シンコペーション、ブレイクを表現できない。そのため、BPMから等間隔の拍を生成するのではなく、音声から時間軸上の拍候補を推定し、拍位置を編集可能な `BeatMap` として保持する。

`BeatMap` の候補データ:

- 各拍の時刻、フレーム、強さ、推定信頼度
- 小節頭・強拍・拍番号（推定できる場合）
- 区間ごとのテンポ推定値
- 音声開始位置に対する拍オフセット
- 自動推定値と手動補正値の区別

BPMは `BeatMap` から表示・検索用に導出する要約値とし、可変テンポの曲では各拍の位置を優先する。拍子や小節頭が正しく推定できない曲では、拍位置だけを保持し、小節情報は未確定でもよい。

### 音声解析の役割分担

処理経路は次のように分ける。

~~~text
音声
  ↓
音量 / スペクトル / MFCC / spectralFlux などの特徴量
  ↓
オンセット・拍候補の検出
  ↓
区間ごとのテンポ追跡と拍列の補正
  ↓
編集可能な BeatMap
  ↓
タイムライン表示 / スナップ / モーション生成・キー削減
~~~

Meydaは、Web Audio APIまたは音声バッファからRMS、スペクトル特徴、MFCC、spectralFluxなどを抽出する候補である。Meyda自体はBPMや拍列を確定する機能ではないため、拍のピーク検出、ハーフ / ダブルテンポの候補比較、区間ごとの追跡はMMD_modoki側の `BeatTrackingService` として分離する。

- [Meyda公式リポジトリ](https://github.com/meyda/meyda)
- [Meydaの音響特徴量一覧](https://meyda.js.org/audio-features)

Essentia.jsにはBPMと拍位置を返すリズム解析機能があるが、Essentia.js本体はAGPL-3.0で、Essentia公式も商用利用や依存ライブラリについて別途確認を求めている。MMD_modokiの標準経路へ直接同梱するより、将来の外部解析、BeatMapインポート、または明確に分離したExperimental経路の候補とする。

- [Essentia.js公式リポジトリ](https://github.com/MTG/essentia.js)
- [Essentiaのライセンス情報](https://essentia.upf.edu/licensing_information.html)

### 推定結果は「編集可能な候補」とする

ボカロ曲やダンス向け楽曲では、音量ピークが必ずしも振付上の拍とは一致しない。自動推定を正解として固定せず、次の操作を用意する。

- 拍の移動、追加、削除
- 音声開始位置の拍オフセット調整
- BPMの倍 / 半分候補の切り替え
- 推定信頼度の低い拍の表示切り替え
- タップ入力による手動拍打ち
- 外部解析した拍列のインポート

自動拍、手動拍、確定済み拍を内部で区別する。自動推定をやり直しても、手動で固定した拍は維持できるようにする。

### タイムラインへの表示

既存の音量波形へ拍線を直接描き込むのではなく、表示レイヤーを分ける。

- 音量波形レイヤー: 音量・波形ピーク
- 拍グリッドレイヤー: 拍、小節頭、推定信頼度
- モーションレイヤー: ボーン、カメラ、モーフのキー

通常の拍は細い線、強拍や小節頭は太い線・色違いとする。1/2拍・1/4拍の細分表示は切り替え可能にし、推定中の拍は薄く表示する。拍線をクリックすると該当フレームへ移動でき、キー登録時には「拍へスナップ」を明示的に有効化できるようにする。

音声解析は再生フレームごとに行わず、音声読み込み後にWorkerまたはオフライン処理で実行し、結果をキャッシュする。表示範囲の拍だけを描画して、波形の再描画と解析処理を分離する。

### モーション・カメラへの利用

拍は自動処理を強制する基準ではなく、キー候補と保護点として使う。

全フレームへベイクしたモーションを間引く場合:

1. 位置・回転の誤差を基準に通常のキー削減を行う。
2. 手動キー、足接地、方向転換、極値、ループ境界を保護する。
3. 強拍や指定した細分拍に近いキーを、誤差が許容範囲なら拍位置へ寄せる。
4. 拍に合わない細かい表現は無理に丸めず、最大誤差と手動キーを優先する。

これにより、拍オフセットは波形表示だけでなく、全打ちモーションのキー間引き、カメラ追従キーの生成、モーフの自動キー生成でも共有できる。可変テンポの曲では、単一BPMからフレーム間隔を計算せず、`BeatMap.beats[]` の実時刻を使う。

利用候補:

- 足の接地やステップを拍へスナップする
- カメラ移動の開始・停止を小節や強拍へ寄せる
- サビなど音量・密度が高い区間でカメラや表情の自動生成を強める
- モーションのループ境界を小節境界へ合わせる
- 拍の細分を使って手拍子、首振り、表情変化を生成する

拍スナップは「なし / 弱く寄せる / 強く寄せる」のようなモードを持たせ、生成キーを直接上書きせず、既存の自動補完・カメラ追従と同じくプレビュー後に1 Commandでベイクする。

## カメラモーション

カメラは、MMDのカメラVMDが持つ X / Y / Z / 回転 / 距離 / FoV のチャンネルを正本とする。現在のカメラVMD経路では評価用 MmdCamera と表示用 ArcRotateCamera を分けているため、追従計算も評価側のカメラモーションに対する補正として扱う。

### 追従モード

#### 注視点追従

カメラ位置は元のカメラキーを保ち、注視点だけをモデルまたはボーンへ追従させる。

- 顔、上半身、センターなどを対象にできる。
- カメラ位置が固定されるため、既存カメラモーションを壊しにくい。
- 顔だけを対象にすると首振りを拾いやすいため、初期値は上半身またはセンターが安全。

#### 軸限定の位置追従

キャラクターの移動差分を、カメラ位置または注視点へ X / Y / Z 軸単位で適用する。

~~~text
delta(frame) = anchor(frame) - anchor(referenceFrame)
newValue = baseValue + selectedAxes(delta) * strength
~~~

例えば X のみを選ぶと、横方向の移動だけをカメラへ伝えられる。Yだけを切れば、ジャンプや段差にカメラが引っ張られない。

#### 位置 + 注視点追従

カメラ位置と注視点へ同じ移動差分を適用し、キャラクターとの画角を保ったまま追従する。位置側と注視点側の軸を独立指定できるようにすると、追従の表現力が上がる。

#### フル追従

キャラクターの移動、注視点、距離、FoVまで自動調整するモード。便利だが、手付けカメラを大きく書き換えるため、初期実装の対象外または Experimental とする。

### 追従設定の候補

- 対象モデル
- 対象ボーン
- 追従範囲
- 基準フレーム
- 位置側の追従軸 X / Y / Z
- 注視点側の追従軸 X / Y / Z
- 追従強度
- ワールド / ローカルオフセット
- スムージング量
- 追従の遅れ
- 手動カメラキーを保護するか

基準フレームは範囲開始フレームを初期値にする。これにより、追従機能を有効にした瞬間のカメラジャンプを抑える。

### カメラのスムージング

単純な移動平均より、追従の遅れを表現できる平滑化を優先する。

- 応答速度
- 遅れ時間
- 追従強度
- 最大移動量

を独立して調整できるようにする。

処理順は、元カメラを先に評価してから追従差分を適用し、その後にスムージングを行う。スムージング済みの結果をカメラキーへベイクする。

### カメラキーの自動生成

最初は指定範囲の全フレームへキーを生成してよい。連続した追従軌道を確実に保存でき、VMD出力との比較もしやすい。

その後、次の最適化を追加する。

- 位置軌道の誤差が小さいキーを削除する
- 方向転換、停止、カット前後のキーを保護する
- X / Y / Z / 回転 / 距離 / FoVを独立してキー削減する
- 近似誤差の許容値をユーザーが指定できるようにする
- 生成された軌道からMMDの補間値を推定する

カメラの回転をEuler角だけで平滑化すると、角度の折り返しやジンバルロックが起きる可能性がある。内部では注視点やクォータニオンを使って計算し、最終段階でMMDカメラの回転値へ変換する。

### カメラの手動編集との共存

- 手動キーを保護する設定を持つ。
- 追従を再計算するときは、元カメラと追従設定から再生成する。
- すでにベイクされたキーへさらに追従を重ねて二重適用しない。
- カメラカットに相当する大きな移動・回転差は自動削減で丸めない。

カメラをモデルのボーンへ単純に親子付けするのではなく、最終的には通常のカメラモーションへベイクする。これにより、ベイク後のカメラを手動編集でき、VMD出力にも接続できる。

## Babylon.js の利用範囲

### 使える汎用機能

Babylon.js の Animation API には、次のような低レベル機能がある。

- Vector2 / Vector3 / Quaternion / Matrix の補間
- Quaternion の球面線形補間
- 接線を使った3次Hermite補間
- Easing function
- 指定フレームのアニメーション評価
- ループ、ブレンド、加算アニメーション
- アニメーショングループの対象マスク

参照:

- [Babylon.js Animation API](https://doc.babylonjs.com/typedoc/classes/BABYLON.Animation)
- [Babylon.js IAnimationKey](https://doc.babylonjs.com/typedoc/interfaces/BABYLON.IAnimationKey)
- [Babylon.js AnimationPropertiesOverride](https://doc.babylonjs.com/typedoc/classes/BABYLON.AnimationPropertiesOverride)
- [Babylon.js BoneIKController](https://doc.babylonjs.com/typedoc/classes/BABYLON.BoneIKController)

これらは、次の用途に向いている。

- 補間結果のプレビュー
- 行列・クォータニオンによる姿勢変換
- カメラ追従のワールド座標計算
- 足先・手先のIK試作
- 加算的な姿勢補正
- 補正済み姿勢をサンプリングしてキーへベイク

### そのまま正本にしないもの

Babylon.js の汎用 Animation は、MMDのVMDトラックそのものではない。

- MMDのボーン・カメラ補間はVMD固有のチャンネル別ベジェ曲線を持つ。
- PMXの付与親、IK、表示枠、物理切替、MMDランタイム評価順は汎用Animationだけでは表現できない。
- Babylon.js の Skeleton.copyAnimationRange は、公式説明でも完全なリターゲットではなく、非常に似た骨格向けとされている。
- IKコントローラーはプレビューやベイクの補助には使えるが、MMDのIK仕様・物理・VMD出力を置き換えるものではない。

したがって、Babylon.js で計算した結果を MMD_modoki の MotionDocument へ戻すアダプターが必要になる。既存のVMD補間とランタイム挙動を守る場合は、Babylon.js AnimationGroupへ一度全面変換するより、MmdAnimation / VMD trackを正本にして、Babylon.jsを評価・補正の補助に使う方が安全である。

- [Babylon animation retarget research](./babylon-animation-retarget-research-2026-06-15.md)
- [現行MMDキーフレーム/ボーン操作/補間曲線 調査メモ](./mmd-keyframe-bone-interpolation-research.md)
- [補間カーブ仕様と実装メモ](./interpolation-curve-spec-implementation.md)

## データ・Command・保存方針

### プレビューとベイクを分ける

追従設定や自動補完設定を変更しても、プレビュー中は正本のキーを変更しない。

- プレビュー: 設定から毎フレーム結果を計算する
- ベイク: 計算結果を通常キーへ変換する
- Undo / Redo: ベイク全体を1 Commandとして扱う

最初から複数の非破壊補正レイヤーを永続化する必要はない。まずはプレビュー、ベイク、Undo、VMD出力の一周を成立させる。

### 再計算時の二重適用を避ける

- ベイク前の元モーションを基準に再計算する。
- 追従済みキーへ追従差分を再度加算しない。
- 生成キーの由来を内部メタデータで追跡できる構造を検討する。
- VMDへ出力する際は、生成元メタデータではなく通常のキーと補間値へ変換する。

### プロジェクト保存

将来、補正レイヤーを非破壊で保存する場合は、次の値をプロジェクト状態に保存する。

- 補正種別
- 対象モーション / カメラ
- 対象ボーン
- フレーム範囲
- 補正量・追従軸
- スムージング設定
- 基準フレーム
- ベイク済みかどうか

アプリ全体の既定値と、作品ごとの再現に必要な設定は分けて保存する。

## 検証観点

### モデルモーション

- 前後キーの間で位置・回転が連続する
- 回転が長い経路へ飛ばない
- 足接地区間で足裏が滑らない
- 手動キーが自動補完で上書きされない
- 物理ボーンへ直接キーを入れたことで物理が二重適用されない
- ベイク前後で見た目とフレーム評価が一致する
- 出力したVMDを再読込して補間が大きく変わらない

### カメラモーション

- 追従開始時にカメラがジャンプしない
- X / Y / Zの選択が独立して効く
- 注視点追従だけではカメラ位置が変わらない
- 手動カメラキーと自動追従の合成規則が明確である
- カットや大きな方向転換が自動削減で壊れない
- 距離・FoV・パースの扱いが維持される
- ベイク後のカメラキーを通常のカメラ編集で修正できる

### 音楽同期

- 音量波形と拍グリッドの横位置が同じ音声時刻を指す
- 音声開始オフセットを変更しても、波形・拍・キーの対応が一貫する
- 可変テンポ区間で、単一BPMの等間隔グリッドに戻らない
- ハーフ / ダブルテンポ候補を切り替えても手動固定した拍が壊れない
- 低信頼度の拍を表示上区別できる
- 手動で追加・移動した拍が自動再解析で保持される
- 全打ちモーションのキー削減で、手動キー・接地・方向転換が保護される
- 拍スナップを無効にした場合、通常の誤差ベースのキー削減結果を保てる
- BeatMapを使ったカメラ・モーフ生成が二重適用されない

## 方針のまとめ

MMD_modokiで優先するのは、外部形式の汎用アニメーション機能よりも、MMDのモーションを「読み込む、直す、カメラを合わせる、書き出す」一周を成立させることである。

そのため、最初の現実的な組み合わせは次のとおり。

- モデル: XYZ補正、短区間補間、足接地補正
- カメラ: 注視点追従、軸限定位置追従、スムージング、キーへのベイク
- 音楽: 音量波形、BeatMap、拍スナップ、拍を考慮したキー削減
- Babylon.js: 補間・姿勢計算・IK・プレビューの補助
- MMD_modoki: MotionDocument、VMD補間、PMX評価、Command、保存、VMD出力

この境界を守れば、Babylon.js側の機能を試しながら、MMD編集の正本と出力互換性を失わずに拡張できる。
