# 出力改善計画

作成日: 2026-08-04
状態: 計画 / 一部未着手

## この計画の役割

書き出し周りの検討が、静止画・透過・動画形式・速度と複数の話題にまたがったため、全体像と優先順位を1本に整理する。

個別の実装指示は [WebGPU 動画書き出し Phase 0 計測 / Phase 1 作業指示](./webgpu-yuv-phase1-work-order-2026-08-04.md) を参照。

## 全体像

### 出口が詰まっている

MMD_modoki の編集機能は増えてきたが、成果物を外に出す経路が両方詰まっている。

- **動画を作る人** → VMD が出せないため、モーションを持ち帰れない
- **静止画を作る人** → ビューポートサイズのスクショしか出せない

MMD_modoki の最大の強み（WebGPU、PBR、FrameGraph のポストエフェクト）を最も評価するのは静止画を作る層である。にもかかわらず、その層に対する出口が最も貧弱になっている。**強みと出口が繋がっていない。**

VMD 出力は別軸だが、静止画側の出口は VMD を待たずに開けられる。

### 5つの需要が1本の改修に乗る

以下はすべて「レンダリング結果を高速・高品質に取り出す」という同じ経路の上にある。

1. 静止画の高解像度書き出し
2. 静止画のアルファ付き書き出し
3. 透過付き動画（キャラと背景を分けて後段で合成したい）
4. 可逆な中間形式としての連番出力
5. 書き出しが遅くてイライラする、という実感

個別機能として数えると5件だが、実体は1つの経路の改善である。

## 最優先: ボトルネックの正体を確定させる

**現時点で、書き出しが遅い原因が確定していない。** ここが決まらないと打ち手が選べない。

### 現状わかっていること

- 2026-04-22 の WebM 実測: draw 十数ms / **capture 90ms 前後** / encode 1ms 前後
- capture の内訳は `mapAsync` 待ちが支配的とされている
- 1920x1080 RGBA8 は 8.3MB。**転送量としては 1ms 未満で運べる量であり、90ms を転送時間で説明できない**
- パイプライン化（staging バッファのリング化）は過去に試したが改善しなかった
- 連番PNG仕様メモ（2026-02-24）の「現状の制限3」に、**高負荷シーンではGPUキャプチャ側が律速になる**と既に記載がある

### 仮説

`mapAsync` は対象バッファに関わるコマンドが全て完了するまで解決しない。draw のコマンドを積んだ直後に待つ構造なら、**GPU のレンダリング時間そのものが capture に計上される。**

現状の draw 計測値が「submit までの CPU 時間」であれば、SSAO / SSR / Bloom の実行時間はどこにも現れず、すべて capture の中にいることになる。パイプライン化が効かなかったこととも整合する（GPU が律速なら並べても縮まない）。

### 判定

空シーン（モデルなし、ポスト全OFF）で同条件の書き出しを実行し、capture を測る。

| capture    | 解釈            | 打ち手                               |
| ---------- | ------------- | --------------------------------- |
| 数ms に落ちる   | GPU 律速        | 出力経路ではなくレンダリング側の最適化。RGBA→YUV は逆効果 |
| 90ms 付近のまま | 転送 or CPU 側処理 | 出力経路の改善が効く。Phase 1 へ              |
| 中間         | 両方            | 両方効くが期待値は下がる                      |

**結果がどちらであっても記録に残す。** GPU 律速だった場合、VP8 実験メモの前提（主犯は readback）の訂正になる。

## 段階

### 段階1: 計測（クォータほぼ不要）

1. **WebM 側の切り分け計測**（上記の判定）
2. **連番PNG の内訳計測を実装する** — capture / encode / save を別々に ms 表示する。これは連番PNG仕様メモの「今後の改善候補4」として半年前から未着手のまま残っている項目である
3. **連番PNG が WebGPU copy 経路に乗っているか、コードを読んで確認する**

3 について: 連番PNG仕様メモは 2026-02-24 更新で、WebGPU copy 経路の導入（2026-04-22）より前である。実装確認の結果、連番PNGは当時の Babylon の RenderTargetTexture / readPixels 経路のままで、**WebM のために作った webgpu-copy 経路を使っていないことが確認できた。**

### 2026-08-06 実測追記

- WebM は空シーン・1920×1080・100フレームで、webgpu-copy の exporter wall-clock が 4118.7 ms、readpixels が 19431.3 ms。readback と CPU pixel transform を分離して記録できた。
- 連番 PNG は同条件で 100 フレーム出力に成功した。wall-clock は 103156.0 ms、capture は 100375.8 ms、PNG encode は 6551.3 ms。capture が支配的である。
- 連番 PNG は WebM の webgpu-copy を使わず、Babylon の RenderTargetTexture / readPixels 経路を使っていることをコード確認した。
- 追加の経路診断では、WebM は current render pass の `bgra8unorm` color attachment（usage 17）を `engine.readPixels` で読み、PNG は `rgba8unorm` の `screenShot` RenderTargetTexture（usage 23）を生成・readback・破棄していた。PNG の遅さを WebM と同じ BGRA→RGBA swizzle の問題として扱う根拠はない。
- キュー上限の比較では queue limit 16 の実ピークが 1 で、queue limit 1 は 720p / 1080p とも wall-clock と readback を悪化させた。キュー拡大より、WebM は swizzle/readback、PNG は RTT lifecycle の調査を優先する。
- 詳細なログ値と判定は [2026-08-06 実測結果](./webgpu-yuv-preinvestigation-2026-08-06.md#2026-08-06-実測結果) に記録した。I420 prototype と代表モデル・モーションの計測は未着手。

### 段階2: 静止画の高解像度・アルファ書き出し（v0.2.2 候補）

**速度問題を回避したまま、高解像度まわりの課題だけを先に解ける。** 1枚なら数秒待てるため、readback の遅さが問題にならない。ここで得た知見は後で動画側に効く。

仕様案:

- **解像度指定**: アスペクト比の選択は既存にあるため、追加で必要なのは **長辺のピクセル数のみ**。1920 / 2560 / 3840 / 7680 / カスタム。両方指定させるとアスペクト比設定と衝突する
- **上限は 8K**。`device.limits.maxTextureDimension2D` を読んで UI に実際の上限を出す。決め打ちしない。超える指定は fail-closed で断る（GPU の OOM はレンダラごと落ちるため、事前に見積もって止める）
- **アルファ付き出力**（B2 で v0.2.x へ送った項目の回収）
- **スーパーサンプリング**: 2倍・4倍で描いて縮小。静止画専用の贅沢として有効

### 段階3: ポストエフェクトの解像度基準（段階2と同時に必要）

出力解像度を変えると絵が変わる問題。

**要調整（ピクセル単位で持っているもの）**

- Bloom / DoF / Luminous のぼかし半径
- Sharpen のカーネル
- Edge blur
- **Offset Rim / Offset Shadow のオフセットと Thickness**
- SSAO のブラー半径（サンプル半径がワールド空間ならそちらは不要）
- Grain の粒サイズ

**不要**

- LUT、Vignette、UV 基準の Distort

実装方針:

- `renderScale = 出力高さ / 基準高さ` を1本用意し、**適用の瞬間に掛ける**
- **保存値は書き換えない。** スケール済みの値がプロジェクトに焼き付くと、次に開いたとき絵が壊れる
- **基準はビューポート高さにしない。** ウィンドウサイズで変わる。固定の基準解像度（1080 など）を決め、プレビューも書き出しも同じ比で計算する
- 各エフェクトが「自分のパラメータはピクセル基準か正規化済みか」を申告する形にすると、後からエフェクトを足すときに毎回考えなくて済む

確認方法: 同じフレームを 1080 と 2160 で書き出し、2160 を 1080 に縮小して並べる。ピクセル完全一致は取れないため**手動チェックリスト行き**とする。

なお、これは既に潜在バグの可能性がある。ウィンドウサイズを変えると絵が変わっていないか確認すること。だとすれば高解像度書き出しはそれを顕在化させるだけで、直せば両方解決する。

**この変更は絵が変わる変更であり、ユーザーが少ない今のうちに入れるのが安い。**

### 段階4: 連番PNG の再チャレンジ

**捨てるつもりだった機能だが、透過・可逆中間・高解像度のすべてを兼ねるため主役になりうる。**

作業内容は、新規実装がほとんどない。

1. WebGPU copy 経路への繋ぎ変え（段階1-3 の確認結果次第）
2. **PNG エンコードを main プロセスから追い出す** — 現状 `nativeImage.toPNG()` を main で実行している。`ioWorkerCount = 4` は `fs.write` の並列化であり、エンコード自体は main のイベントループを直列で塞いでいる可能性がある。main が詰まると IPC も進捗通知も止まるため、体感の悪さにも寄与しうる。`utility process` か `worker_threads` へ
3. **圧縮レベルの選択**（高速 / 標準 / 小さい）。連番PNGはフレーム間に依存がないため並列化が最も効く。後で再エンコードする前提なら多くの人は高速を選ぶ
4. 出力解像度の可変化（段階2と共通）

### 段階5: RGBA→YUV の GPU 前処理（Phase 1）

今回の空シーン計測では、WebM の webgpu-copy に CPU pixel transform 約 10ms/frame と GPU readback 約 10ms/frame が見えているため、出力経路の改善余地はあると判断する。RGBA→I420 の GPU 前処理は実装価値があるが、readback が残るため単独で決定打にはならない。compute / staging / map / VideoSample のコピーを含む総時間で、RGBA baseline を下回るか確認してから採用する。詳細は [作業指示](./webgpu-yuv-phase1-work-order-2026-08-04.md)。

30fps・1920×1080 の 3 分動画では、GPU swizzle のみで理論約 54 秒、I420 化による readback 削減まで含めた理論最大で約 88 秒の短縮余地がある。追加コストを含む実用上の期待値は 45〜80 秒程度と仮置きできるため、Phase 1 は試す価値がある。ただし、これは空シーンの 100 フレーム計測からの見積もりであり、readback のデータ量依存性と代表モデルでの効果は未確認である。

環境依存がないため、動く環境なら全ユーザーが同じだけ速くなるという利点がある。

### 段階6: 動画形式の拡張（先送り）

AV1 対応、ハードウェアエンコーダ経路、無圧縮AVI をまとめて扱う回。現時点では着手しない。

## 透過書き出しの課題

透過付き動画のフォーマットは実質的に選択肢がない。

| 形式               | 透過 | 実用性             |
| ---------------- | -- | --------------- |
| WebM (VP9 alpha) | 可能 | 編集ソフト側の対応が薄い    |
| 無圧縮AVI (BGRA)    | 可能 | 読み手のアルファ対応がまちまち |
| ProRes 4444      | 可能 | エンコーダを用意できない    |
| ハードウェアエンコーダ      | 不可 | 原理的に扱えない        |
| 連番PNG            | 可能 | どこでも読める         |

**連番PNGが実質の正解。** 新しい形式を作る必要はなく、連番PNGが実用的な速度で出ればよい。

レンダリング側に3つ課題がある。

1. **Bloom が透明部分に滲む。** 合成したとき背景の上に光の輪が出る。アルファ出力時にどのポストを通すかの判断が要る
2. **乗算済みアルファ。** レンダラ出力は premultiplied だが PNG 仕様はストレートアルファ。`rgb / a` で戻す必要があり、a が小さい箇所（髪の先など）でノイズが出る
3. **影の落ちる先がない。** 背景を透明にすると床が消え、影も消える。**「影だけ受ける床」**が要る（Babylon の ShadowOnlyMaterial 相当）。アクセサリの一種として置けるようにするのが素直

## 動画形式の整理

|             | 解くこと                | 状況                                     |
| ----------- | ------------------- | -------------------------------------- |
| VP8 / WebM  | 現行                  | ハードウェアエンコーダがほぼ無い                       |
| H.264 / MP4 | 編集ソフトが読める           | ライセンスの確認が要る                            |
| AV1         | ロイヤリティフリー、圧縮効率、HW経路 | 編集ソフト側の対応は H.264 ほど厚くない                |
| 無圧縮AVI      | ライセンス不要、エンコードコスト0   | 4GB の壁（1080p30 で約22秒）、OpenDML 対応が事実上必須 |

**AV1 と MP4 は別の問題を解いている。** AV1 を入れても「編集ソフトに持っていけない」問題は残る。同じ回に扱うとしても、そこを混同しない。

無圧縮AVI は、一番大きい需要である透過に応えられず、かつ OpenDML の実装コストがある。**連番PNGが速くなれば不要**という判断が現時点の結論。やらない理由として記録しておく。

## やらないこと

- **VP8 の自作エンコーダ（Phase 2 以降）** — 段階1〜5 を通過してから判断する。手前にやっていないことが複数ある
- **無圧縮AVI** — 上記理由。連番PNGの高速化が代替になる
- **ハードウェアエンコーダ経路** — 環境依存があり、経路が二本立てで恒久的に残る。AV1 対応と同じ回にまとめる
- **出力パイプラインの抽象化** — 形式が1つしかない状態で分けると切れ目を間違える。2つ目の形式を足すときにやる
- **RAW 書き出し** — 目的（高ビット深度・どこでも開ける）は TIFF / 16bit PNG / EXR が満たす。RAW を足す理由が残らない

## 未決定事項

- 16bit PNG を入れるか（Bloom のバンディング対策。Canvas 経路では出せないため PNG エンコーダの自前化が必要。ただし既に生バイトを読んでいるため材料は揃っている。レンダーターゲットが 8bit のままなら意味がない点に注意）
- OpenEXR を入れるか（静止画のみ。動画では 8K half float RGBA で1枚約265MBとなり非現実的）
- 深度パス出力を入れるか（SSAO/DoF 用に深度は既にある）
- 高解像度書き出しを「最終キャンバスを撮る」ではなく「**指定したテクスチャを撮る**」形で作るか。そうすれば EXR・深度・16bit を後から「対象と形式を変えるだけ」で足せる。今やる必要はないが、扉を開けておくコストはほぼゼロ
- 連番PNGのアルファと段階2の静止画アルファで、実装をどこまで共有するか
