# 床・ステージ表面構想メモ

## 目的

現在の標準床と MirroringFloor を同じ操作導線にまとめ、将来の海面・湖面・雪面を追加できる形に整理する。

ここで扱う「床」は、単一の mesh や Material を指すものではない。編集補助、画面上の見た目、物理衝突では責務が異なるため、UI は統合しても内部状態と実行経路は分離する。

本メモは構想段階の設計記録であり、海面・湖面・雪面の実装を確定するものではない。2026-08-02 に雪面と、水面・雪面で共有する接触検出案を追記した。

## 結論

- UI は「床・ステージ表面」の詳細ポップアップへ統合する。
- 内部では、編集用床、ステージ表面、物理床を別レイヤーとして扱う。
- 最初の表面候補は、標準床、鏡面床、海面、湖面、雪面に絞る。
- 海面と湖面は別実装ではなく、同じ水面 Material のプリセット差として扱う。
- 雪面は Material だけでも成立する候補とし、足跡と小さな雪煙を任意の接触エフェクトとして検討する。
- 水面と雪面の接触エフェクトは、物理衝突イベントではなく足ボーンと表面平面の位置関係から検出する方針を第一候補とする。
- 水中表現は対象外とし、必要になった場合は別エフェクトとして検討する。
- 芝生・草原は初期候補から外す。平面テクスチャだけでは独立プリセットにする意義が弱く、立体的な草は床 Material とは別の地表装飾機能になるためである。

## 責務の分離

### 1. 編集用床

現在のグリッド床に相当する。

主な責務:

- 座標とスケールの確認
- モデル配置時の基準面
- 編集中の視認性確保
- 影の受け面

ステージ表面を有効にした際は重なりや z-fighting を避ける必要がある。編集用床の保存状態は維持したまま一時的に非表示にする、または表示オフを促す方針を検討する。

### 2. ステージ表面

最終画面に見せるための表面オブジェクト。

候補:

- 鏡面床
- 海面
- 湖面
- 雪面
- 将来の標準床外観プリセット

反射用 render target や水面 Material など、種類ごとに描画経路が異なる。UI 上で同じドロップダウンから選択できても、単一 Material へ無理に統合しない。

### 3. 物理床

モデルや物理剛体を支える衝突面。

見た目の表面とは独立させる。特に、水面の高さを変えたことでモデルの立つ高さまで変わる挙動は避ける。

- ステージ表面の高さ変更は物理床へ自動反映しない。
- 海面・湖面・雪面は、見た目の表面を作っただけでは新しい衝突面を生成しない。
- 将来同期機能を追加する場合も、明示的な「物理床と高さを同期」操作とする。

## UI 構想

右パネルなどの簡易導線には、表示状態、現在の種類、詳細ボタンだけを置く。各設定は「床・ステージ表面」の詳細ポップアップへまとめる。

### 種類

初期候補:

1. 標準床
2. 鏡面床
3. 海面
4. 湖面
5. 雪面

実装上は、次のような階層として扱う。

```text
表面方式
├─ 標準
├─ 鏡面
├─ 水面
│  ├─ 海プリセット
│  └─ 湖プリセット
└─ 雪面
```

UI のドロップダウンでは、利用者が迷わないよう「海面」「湖面」を直接選択肢として表示してよい。

### 共通設定

- 表示 ON / OFF
- 形状: 四角 / 丸
- 広さ
- 高さ

種類によって意味を持たない項目は無効表示にするか、種類別セクションへ移す。

### 鏡面床

既存の MirroringFloor 設定を引き継ぐ。

- 形状: 四角 / 丸
- 広さ
- 高さ
- 反射率
- 反射解像度

高さはすでに `mirroringFloorHeight` として実装され、詳細ダイアログ、プロジェクト保存、読み込みに対応している。UI 統合時は新規状態を増やさず、既存設定を移設する。

鏡面床は SSR ではなく `MirrorTexture` による平面反射を使用する。グローバルな Frame Graph SSR の ON / OFF と連動させない。

### 海面・湖面

同じ水面実装を共有し、初期値だけをプリセットとして分ける。

共通候補:

- 形状
- 広さ
- 高さ
- 水の色
- 透明度
- 波の高さ
- 波長または波の細かさ
- 波の速度
- 風向・風力
- 反射品質

プリセットの方向性:

| プリセット | 見た目の方向性 |
|---|---|
| 海面 | 沖縄の海を意識した高彩度の青緑、明るい浅瀬色、比較的大きい波 |
| 湖面 | 彩度を抑えた青緑または深緑、弱い波、落ち着いた反射 |

Babylon.js の `WaterMaterial` は独自の反射・屈折用 render target を持つため、画面全体の SSR を水面反射の前提にしない。MMD モデルとの相性を優先し、写実性より色調整のしやすさと負荷の安定を重視する。

### 水中表現

初期スコープには含めない。

水中表現には、少なくとも色吸収、距離フォグ、コースティクス、画面全体の色補正、カメラが水面を横切る判定などが必要になる。これは水面 Material のプリセットではなく、独立した環境・ポストエフェクトとして検討する。

水面の高さを変更しても、水中エフェクトを自動的に有効化しない。

### 雪面

芝生と異なり、雪は平面 Material でもノーマル、粗さ、陰影、微細な反射によって立体感を出しやすい。そのため、独立した初期候補に含める。

初期設定候補:

- 雪の色
- 青みのある陰影
- 粗さ
- 表面ノーマルの強さ
- 微細なきらめきの強さ
- 足跡 ON / OFF
- 雪煙 ON / OFF

初期スコープでは地形 mesh や物理形状を変形させない。足跡は表面用の動的 mask texture へスタンプし、法線または色の差として見せる方式を第一候補とする。雪煙は接触開始時や強い踏み込み時だけ生成する小規模な particle effect とする。

本格的な沈み込み、除雪、雪の堆積、モデルの脚が雪へ埋まる深度表現は対象外とする。

## 水面・雪面の接触検出案

### 物理衝突との区別

接触エフェクトのために必要なのは、剛体を押し返す物理衝突ではなく「どの足が、表面上のどこへ、どの程度の速さで触れたか」という通知である。

現在の `PhysicsRuntimeController` は、`babylon-mmd` の Bullet `MultiPhysicsRuntime` へ `PhysicsStaticPlaneShape` を追加して物理床を作っている。この経路では床との物理衝突は成立するが、アプリ側は接触点の通知を購読していない。

Babylon.js Physics V2 には接触点、法線、衝撃量を含む collision event と raycast がある。一方、現在の MMD 物理経路は Babylon.js Physics V2 の標準 body を直接使う構成ではない。水面・雪面の演出だけを目的に物理 backend を組み替えたり、内部の Bullet manifold へ依存したりしない。

参考:

- [Babylon.js `IPhysicsCollisionEvent`](https://doc.babylonjs.com/typedoc/interfaces/BABYLON.IPhysicsCollisionEvent)
- [Babylon.js `IPhysicsEngine.raycast`](https://doc.babylonjs.com/typedoc/interfaces/BABYLON.IPhysicsEngine)

### 第一候補: 足ボーンと表面平面による検出

水面と雪面で共有する小さな `StageSurfaceContactDetector` を設ける。

入力:

- 左右の足首・つま先ボーンのワールド座標
- 直前フレームの座標
- ステージ表面の高さ
- 四角 / 丸と広さ
- 接触しきい値と離脱用 hysteresis

出力:

- `enter`: 表面へ触れた
- `stay`: 表面付近に接触し続けている
- `exit`: 表面から離れた
- 足の識別
- 表面上の XZ 座標
- おおよその接触速度

利用例:

| 表面 | `enter` | `stay` | `exit` |
|---|---|---|---|
| 海面・湖面 | 波紋、速度が大きい場合は水しぶき | 必要なら弱い連続波紋 | 原則なし |
| 雪面 | 足跡、速度が大きい場合は雪煙 | 滑り移動時の短い軌跡 | 原則なし |

これは視覚エフェクト用の判定であり、物理床の高さや剛体運動へ影響させない。表面ごとの反応は detector 本体へ直接書かず、水面・雪面側の listener に分ける。

### タイムラインとの関係

接触エフェクトは時間方向に状態を持つため、シーク、逆再生、停止中のポーズ変更に注意する。

初期方針:

- 通常の前方向再生中だけ新しい波紋・足跡・雪煙を生成する。
- シークや逆再生を検出したら contact state をリセットする。
- 停止中のボーン編集では、接触表示を増殖させない。
- 足跡を永続させる場合、再生開始時または明示的なリセット操作で消去する。
- 書き出しで再現性が必要になった場合は、接触イベントの事前 bake または先頭からの逐次評価を別途検討する。

将来、本当に衝撃量や剛体単位の接触が必要になった場合に限り、Bullet plugin の collision event、raycast、または接触情報を取得する専用 adapter を調査する。

## 芝生・草原を初期候補から外す理由

平面へ芝生テクスチャとノーマルを貼るだけなら軽いが、見た目は「緑色の標準床」に近く、専用の表面方式として扱う意義が弱い。

立体的な草を表現する場合は、次の要素が必要になる。

- 大量の grass card、instance、または専用ジオメトリ
- 半透明部分による overdraw
- 風揺れ
- 影の扱い
- モデルの足、スカート、アクセサリとの貫通対策

草一本ごとの物理衝突は行わず、物理的には地面だけを衝突面にするのが現実的である。ただし草丈が長いほどモデルとの貫通が目立つ。

将来追加する場合は次のどちらかに分ける。

- `標準床の外観プリセット`: 芝生、砂浜、コンクリート、木床など
- `地表装飾`: 立体的な草、密度、草丈、風揺れなど

後者は床 Material の種類ではなく、独立した scene object / effect とする。

## 状態設計の方向性

既存プロジェクトとの互換を維持しつつ、概念上は次の状態へ整理する。

```ts
type StageSurfaceType = "none" | "mirror" | "water" | "snow";
type WaterSurfacePreset = "ocean" | "lake";

interface StageSurfaceState {
    enabled: boolean;
    type: StageSurfaceType;
    shape: "square" | "circle";
    size: number;
    height: number;
    waterPreset?: WaterSurfacePreset;
    contactEffectsEnabled?: boolean;
}
```

ただし、鏡面床と水面の runtime object や詳細設定まで共通クラスへ押し込む必要はない。共通化するのは UI 入力と保存形式の上位構造に限定する。

既存値の移行方針:

- 現在の `groundVisible` は編集用床の表示状態として維持する。
- MirroringFloor が有効な既存プロジェクトは、ステージ表面の `mirror` として読み替える。
- 既存の鏡面床詳細値は失わず、そのまま利用する。
- 新しい状態が存在しない旧プロジェクトでは従来表示を再現する。

## 実装段階案

### 第1段階: 既存 UI の整理

- 標準床と MirroringFloor の操作導線を詳細ポップアップへまとめる。
- 内部の `ground` と `mirroringFloor` は別 mesh のまま維持する。
- 初期値、保存、読み込み、表示同期を確認する。

### 第2段階: 水面 PoC

- Babylon.js `WaterMaterial` の WebGPU / WGSL 動作を確認する。
- 海面と湖面の初期プリセットを作る。
- MMD モデル、outline、影、Frame Graph、PNG / WebM 出力との共存を確認する。
- 反射・屈折 render target の負荷を測る。

### 第3段階: 雪面と共通接触検出の PoC

- 雪面 Material の色、粗さ、ノーマル、きらめきを調整する。
- 左右の足首・つま先を使う `StageSurfaceContactDetector` を試作する。
- 水面の波紋と雪面の足跡を、同じ contact event から別 listener で生成する。
- シーク、逆再生、停止中の編集で履歴が増殖しないことを確認する。
- 足跡用 dynamic texture と particle の負荷を測る。

### 第4段階: 必要性を見て拡張

- 標準床の外観プリセット
- 砂浜など水面と組み合わせる背景
- 地表装飾としての立体草
- 雪面の本格的な変形
- 水中エフェクト

いずれも MMD 編集の本筋や出力安定性を壊さない範囲で独立機能として追加する。

## 確認項目

- 表面種類の変更で古い mesh、Material、render target が残らないか。
- 標準床とステージ表面の重なりで z-fighting が発生しないか。
- 表面の高さを変更しても物理床の高さが意図せず変わらないか。
- 鏡面床と水面がグローバル SSR と二重適用にならないか。
- Classic / Frame Graph の切替後も表示状態が同期するか。
- プロジェクト保存・読み込み後に種類と詳細値が復元されるか。
- PNG / WebM 出力に編集用グリッドが意図せず含まれないか。
- 水面の render target が WebGPU validation warning や破棄済み texture 参照を発生させないか。
- 足ボーン名を取得できないモデルで接触検出が安全に無効化されるか。
- 四角 / 丸の範囲外で波紋や足跡が生成されないか。
- シーク、逆再生、停止中の編集で接触エフェクトが増殖しないか。
- 表面の高さ変更後も接触位置と表示位置が一致するか。
- 複数モデルで足跡・波紋の生成負荷が許容範囲か。
