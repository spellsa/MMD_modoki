# v0.2 作業メモ

更新日: 2026-04-27

## 目的

v0.2 系では、v0.1 系のバグ修正ラインとは分けて、Babylon.js と babylon-mmd の新しい機能・改善を取り込む。

単なる依存更新ではなく、MMD_modoki 側で実際に価値が出る機能を有効化・検証することを目的にする。特に babylon-mmd の物理演算まわりを重めモデルでも扱いやすくする。

v0.1.9 は基本的に安定版向けのバグ修正として扱い、v0.2 系の依存更新や挙動変更を不用意に混ぜない。

このメモは、v0.2 で必ず全部実装する約束ではなく、忘れないための候補リストでもある。実装より調査・保留判断・知見の記録で止める項目があってよい。

## 作業ブランチ

- `work/v0.2-dependency-upgrade`

## 基本方針

- MMD 本体機能を優先する
- 汎用 3D アプリ化や実験機能の拡張は、依存更新の安定確認より後に回す
- 大きい依存更新は 1 グループずつ進める
- 依存を上げるだけで終わらせず、取り込む機能と検証結果を明示する
- タスクは「実装するもの」だけでなく、「調査して見送るもの」も含めて管理する
- 破綻が出たら、無理に直し切るより原因範囲と再現条件をメモに残す
- v0.1 系へ戻す可能性がある修正は、v0.2 ブランチ内でも切り分けて考える

## 開発期間の想定

v0.2 は 1 か月程度かけて開発する想定にする。

短期アップデートでは避けたい重めの機能も、この期間なら検証対象に入れてよい。ただし、v0.2 の中心はあくまで MMD 編集・再生・出力体験の改善であり、汎用機能や実験機能は優先度を下げる。

## v0.2 の主テーマ

1. babylon-mmd の新機能取り込み
2. 重めモデル向けの物理演算改善
3. 物理・描画・出力の測定と比較を残す
4. Babylon.js 9 系での WebGPU / MMD 材質 / outline 回帰確認

### Frame Graph 標準化方針

v0.2 では、描画・ポストエフェクト・出力前処理の標準経路を Frame Graph ベースへ寄せることを目標にする。

狙い:

- SSAO / DoF / Bloom / LUT / Fog / LuminousGlow / WebM capture の順序を明示的に管理する
- Babylon 8 時代に RenderingPipeline 内で固定されがちだった DoF などを、差し替え可能な描画タスクとして扱えるか検証する
- WebGPU と WebGL2 fallback の違いを、描画経路ごと比較できるようにする
- 既存の独自 PostFX / workaround を、公式タスクで置き換えられるものと残すものに分ける
- 中間 render target の責務を整理し、WebM 出力や高品質出力専用の経路を作りやすくする

最初の PoC:

- [ ] MMD scene color を Frame Graph 経由で最終出力する
- [ ] depth texture を使う DoF を Frame Graph 上で動かす
- [ ] DoF / Bloom / LUT の順序を 2 パターン以上で比較する
- [ ] MMD outline が DoF 前後どちらに乗るべきか比較する
- [ ] PMX の透過材質、髪、スカート、アクセサリが depth / DoF で破綻しないか確認する
- [ ] WebGPU と WebGL2 fallback で同じ構成が起動できるか確認する
- [ ] WebM capture 用に、画面表示とは別の後段構成を持てるか確認する

移行条件:

- MMD Standard material / toon / sphere / texture / 透過が既存経路と大きく乖離しない
- babylon-mmd の `MmdOutlineRenderer` と競合しない
- WebGPU で起動し、WebGL2 fallback でも最低限の表示が壊れない
- 既存プロジェクト保存値の互換性を壊さない
- Frame Graph が使えない場合に、最低限の描画へ戻せる

注意:

- Frame Graph はエフェクト品質そのものを自動で上げる機能ではなく、描画タスクとリソース依存を整理する基盤として扱う
- DoF は depth texture 依存のため、透過材質や outline との順序で見た目が変わりやすい
- v0.2 では既存パイプラインの即削除ではなく、Frame Graph 経路を標準候補として作り、安定確認後に旧経路を整理する

Babylon.js 8 系や当時の WebGPU 制約に合わせて無理に作った独自実装は、Babylon.js 9 系で公式経路が安定するなら置き換え候補にする。

### babylon-mmd の提供範囲メモ

2026-04-27 時点の `babylon-mmd@1.2.0` と公式ドキュメントを確認した限り、babylon-mmd が直接提供するのは主に MMD モデル / MMD アニメーション / MMD ランタイムの領域である。

babylon-mmd 側にあるもの:

- PMX / PMD / VMD / VPD / BPMX / BVMD の parser / loader
- MMD Standard material
- MMD toon shader
- sphere / toon texture など MMD 材質処理
- material morph 用 proxy
- MMD outline renderer
- SDEF injector / SDEF mesh
- WebGPU / WGSL 対応の MMD material / outline shader
- MMD camera
- model / camera animation runtime
- morph / append transform / IK
- audio sync / player control
- Bullet / Ammo / Havok 物理連携
- WASM runtime / MPR / Buffered evaluation

babylon-mmd 側の提供範囲ではなさそうなもの:

- SSAO
- Bloom
- DoF
- LUT
- Fog
- RSM GI
- AutoLuminous 相当
- MME / post effect 一式
- MMD light keyframe runtime
- self shadow keyframe runtime
- ground shadow / self shadow spec support
- アクセサリ / scene object timeline

したがって、v0.2 の古い回避実装整理では、まず次のように分ける。

- MMD 材質 / outline / SDEF / model runtime は babylon-mmd の更新に寄せる
- SSAO / DoF / Bloom / Fog / LUT / Glow などは Babylon.js 公式機能と MMD_modoki 独自実装の比較対象にする
- Light / self shadow / accessory / scene object timeline は MMD_modoki 側の `modoki-owned tracks` として扱う

### babylon-mmd と MMD_modoki の責務分担

babylon-mmd が提供するタイムライン / animation runtime は、基本的に PMX/PMD モデルと MMD カメラのモーションを扱うためのものとして見る。

babylon-mmd 側に乗せる対象:

- PMX / PMD ボーン
- PMX / PMD モーフ
- Property / IK のうち、babylon-mmd の `MmdPropertyAnimationTrack` と整合する範囲
- MMD カメラ

MMD_modoki 側で自前実装する対象:

- 照明
- セルフ影 / 影設定
- 重力
- アクセサリ
- scene object
- 将来の OBJ / 点群など、MMD モデルではないオブジェクト

このため、v0.2 で増やす非 PMX / 非カメラ項目は `modoki-owned tracks` として扱う。

`modoki-owned tracks` で必要になるもの:

- キーフレーム格納形式
- 補間またはステップ評価の仕様
- 現在フレームの値評価
- scene / UI への値反映
- プロジェクト保存 / 読み込み
- undo/redo との接続
- タイムライン表示上のカテゴリ・色・選択挙動

実装時は、babylon-mmd の runtime に無理に押し込まず、`MMD_modoki` 側で frame evaluation service のような層を持つ案を第一候補にする。

## リスク

- Babylon 9 系では、材質・ポストエフェクト・WebGPU 周辺の細かい挙動差が後から見つかる可能性がある
- `babylon-mmd` 更新により、物理・モーフ・MMD ランタイム内部の挙動差が出る可能性がある
- Electron / Vite / Forge を同時に上げると、ビルド不具合と描画不具合の切り分けが難しくなる
- `@electron/fuses` 2 系は、現行の `@electron-forge/plugin-fuses@7.11.1` の peer dependency と合わない可能性がある
- Babylon 公式機能へ置き換える場合、起動確認だけでは足りない。MMD Standard の Toon 寄せ合成や既存 project の保存値互換を失う可能性がある
- SQLite WASM を undo/redo の中核にすると、操作粒度や副作用分離の問題を DB で隠してしまう可能性がある。そのため、最初はタイムラインの小さい操作に限定して評価する
- 高頻度入力ログを雑に SQLite へ流すと、描画や再生の負荷調査そのものに影響する可能性がある
- OBJ や点群読み込みは、MMD 本体機能ではなく scene object / accessory 寄りの扱いになる。タイムラインや材質 UI に混ぜると scope が膨らむ
- GLTF / GLB で詰まったように、Babylon 側で読み込めることと MMD_modoki の scene / WebGPU / WGSL / UI に統合できることは別問題
- 照明・アクセサリ・セルフ影・重力は babylon-mmd の外側で評価する `modoki-owned tracks` になりやすい。タイムライン UI に出すだけでなく、保存・再生時評価・undo/redo の責務を決める必要がある

## 次の判断

Babylon 9.2 + babylon-mmd 1.2 の実モデル確認が安定しているなら、次は babylon-mmd の Worker 対応物理と、Frame Graph 標準描画パイプライン PoC を並行して試す。

Frame Graph は v0.2 の描画標準候補として扱い、まず DoF / Bloom / LUT / SSAO の順序を動かせる最小構成を作る。

ただし、MMD 材質・outline・透過・WebGL2 fallback が崩れる場合は、旧描画経路を退避経路として残す。

既存の設計メモ:

- [physics-worker-implementation-plan.md](./physics-worker-implementation-plan.md)

SQLite WASM は、v0.2 で undo/redo が未実装の状態から試すなら十分に意味がある。まずはタイムラインのキー追加 / 削除 / 1f移動だけを対象にし、SQLite-backed command history として実装負荷・応答速度・状態整合性を確認する。

ただし、DB を入れても undo/redo の本質である「1 操作の粒度」「逆操作」「副作用の整合」は消えない。PoC の結果、SQLite が重すぎる場合は、既存の [undo-redo-investigation.md](./undo-redo-investigation.md) にある `HistoryManager + command + 最小差分` 方式へ切り戻す。

Electron / Vite major update は、物理 Worker 検証や SQLite WASM 実験と混ぜると切り分けが難しい。先に babylon-mmd の MPR / Buffered 評価の可否を見てから、別コミットで扱う。
