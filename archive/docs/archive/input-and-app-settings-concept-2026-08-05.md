# 入力まわり構想メモ（ショートカット / ゲームパッド / MIDI / アプリ設定の保存）

更新日: 2026-08-05
状態: 構想 / 未実装

## このメモの役割

入力デバイス対応（ショートカットキー、ゲームパッド、MIDI、Stream Deck）と、その前提になるアプリ設定の保存方式をまとめる。実装仕様書ではなく、方向と順序を決めるための設計メモである。

関連: [出力改善計画](./output-improvement-plan-2026-08-04.md) / [モーション補間・自動補完・カメラ追従の構想メモ](./motion-interpolation-camera-follow-concept-2026-08-04.md)

## 前提: アプリ設定の保存場所が未解決

現在の exe 配布はアプリをまるごと入れ替える形のため、**更新時にデータが引き継がれない。**

ショートカットキーの割り当ては典型的な「アプリ全体の設定」であり、プロジェクトファイルに入れるものではない。したがって**入力まわりの機能に着手する前に、アプリ側の永続データの置き場所を決める必要がある。**

これはキーバインドだけの問題ではない。出力プリセット、既定の保存先、UI 言語、最近開いたプロジェクト、ウィンドウレイアウトなど、アプリ全体の設定を1つでも持った時点で同じ問題に当たる。

### 着手前に棚卸しが必要

物理互換補正のドキュメントに「旧 localStorage キーの扱い」の記載がある。Electron の localStorage は userData 配下（`%APPDATA%\<アプリ名>\Local Storage\`）に保存されるため、**アプリを入れ替えても消えていない可能性がある。**

**現状どこに何が保存されているかを先に確認する。** 既存の永続データを把握しないまま器を設計すると二重管理になる。

### 保存場所の方式（案）

**exe の隣に `data/` フォルダがあればそこを使い、無ければ `app.getPath('userData')` を使う。**

- 通常利用 → `%APPDATA%` 配下。**アプリを入れ替えても残る**
- ポータブル利用 → `data/` を自分で作れば**フォルダごと持ち運べる**

判定は起動時に1回、フォルダの存在を見るだけ。ポータブル配布の思想（フォルダ1個で完結、システムに何も残さない）と、更新耐性の両方を殺さない。VS Code が同じ方式を採っている。

### ファイルの分け方（案）

| ファイル          | 中身                            | 性質                           |
| ------------- | ----------------------------- | ---------------------------- |
| settings.json | キーバインド、出力プリセット、言語、既定の保存先      | **ユーザーの意図。**バックアップ・エクスポートしたい |
| state.json    | ウィンドウサイズ、最近開いたファイル、最後に使ったフォルダ | **たまたまの状態。**消えても困らない         |

分ける理由:

- state は書き込み頻度が高い。壊れてもキーバインドは無事でいてほしい
- 「設定をリセット」で state だけ消せる
- エクスポート／インポートの対象が明確になる（settings だけ持ち運べばよい）

### 実装上の要件

- **バージョンフィールドを最初から入れる。**後から足すと「無い＝v1」の特別扱いが永久に残る
- **アトミック書き込み。**一時ファイルへ書いてから rename する。これをしないと書き込み中のクラッシュで JSON が途中で切れ、全設定が飛ぶ
- **壊れていても起動する。**ここは fail-closed にしない。既定値で起動して警告を出す。設定ファイルが原因でアプリが立ち上がらないのが最悪
- **書き込みをデバウンスする。**スライダー操作のたびに書かない

### 今やるのが安い理由

**現時点で移行対象がほぼゼロ。**アプリ側設定をまだ持っていないため、今決めれば移行コードが要らない。後から場所を変えると、旧場所から読んで新場所へ書き写す処理を何バージョンか残すことになる。

「後から変えられないもの」は次の3点のみ。中身の項目はいくらでも足せる。

1. 保存場所の決定方法
2. ファイルの分け方
3. バージョンフィールドの有無

## 自動バックアップ

ユーザーから要望が出ている。本家MMDには無く、MikuMikuMoving にはある機能。

MMD 界隈では「こまめに保存」が民間伝承として共有されており、作業消失の経験が広く共有されている。**プレリリース版のアプリに長時間を投じる心理的ハードルの一部になっている可能性がある。**機能というより、本気で使ってもらうための前提条件に近い。

### 設計で外せない4点

1. **ユーザーのファイルを絶対に上書きしない。**自動保存が本人の保存先を触ると、壊れた状態が正本を潰す。保存先は必ず別
2. **世代を残す。**最も多い事故は「やらかした直後に自動保存が走り、良い方を上書き」。3〜5世代のローテーションにする
3. **クリーン終了マーカー。**正常終了時にフラグを書き、起動時にそれが無くバックアップがあれば復元を提案する。**保存そのものより復帰導線が本体**であり、これが無いとバックアップがあっても気づかれない
4. **保存コストを測る。**全モデルの全キーをシリアライズするため、大きなプロジェクトで何ms かかるかを知らないと、保存のたびに画面が固まる。書き出し中（`ui-export-lock`）は当然止める

置き場所は上記の永続データ領域の隣（`backups/`）。ただし `%APPDATA%` は一般ユーザーには見えない場所なので、**UI から「バックアップフォルダを開く」導線を出す。**

## ショートカットキー登録

エディタとして必須の機能。上級者ほど作業速度が指に乗らないと道具として使えない。

### 実装の本体はコマンドIDの整理

難しいのは割り当てではなく**コンテキスト**である。同じ `Delete` が、タイムラインにフォーカスがあるとき、モデル選択中、ボーン選択中、書き出し中で意味が変わる。

「今どこにフォーカスがあるか」を1箇所で管理する仕組みが要る。これが無いと各所に条件分岐が散る。

設計案:

- **コマンドID**（`timeline.deleteKey` のような文字列）を先に定義する
- **キーバインドは「コンテキスト + キー → コマンドID」の表**として持つ
- **メニュー項目もボタンも外部入力も、すべて同じコマンドIDを叩く**

こうすると入力経路が1本に統合される。既存の Command パターンの上に素直に乗るはず。副産物としてメニューの整理も進む。

### 決めておくこと

- **衝突検出。**同じコンテキストで重複したら警告する。黙って片方が効かないのが最悪
- **既定に戻す。**全体と個別の両方。触って壊した人が帰ってこられる導線
- **本家MMDのキー配列をプリセットとして持つ。**MMD歴の長い人がそのまま入れる。操作体系は互換の対象外だが、選べるようにするのは有効
- **予約キー。**OS 側が持つ組み合わせを割り当てさせるかどうか

## ゲームパッド

**手元に実機があるため、現物で検証できる。**MIDI と Stream Deck には無い利点。

### メーカーごとのボタン配置差について

Gamepad API は `gamepad.mapping === "standard"` を返すデバイスについて、**ブラウザ側で標準配置に正規化済み**である。

- `buttons[0]` = 下のフェイスボタン、`[1]` = 右、`[2]` = 左、`[3]` = 上
- `buttons[6]/[7]` = トリガー（`.value` でアナログ値）
- `axes[0,1]` = 左スティック、`axes[2,3]` = 右スティック

**位置は揃っている。違うのは刻印だけ。**Xbox は A、PlayStation は ×、Nintendo は B（Nintendo は物理的に A/B の位置が入れ替わっている）。`mapping` が `""` のデバイスは正規化されていないため、対応を諦めてよい。

### バインドUIは「押して覚えさせる」

ボタン名を表示しようとすると「どのブランドの呼び方をするか」問題に当たる。**「割り当てたいボタンを押してください」で登録させれば、ブランド差が消える。**キーボードのショートカット登録と同じUIになり、入力デバイスの種類を問わず1つの仕組みで済む。

### ビューポート操作は土台が要らない

ゲームパッドと MIDI は本来「収録の仕組み」を必要とするが、**ビューポートのナビゲーション（見回す、寄る、引く、回り込む）だけは例外**である。キーを打たないため、Gamepad API を読んでカメラを動かすだけで成立する。

追加費用ゼロ（MMD 界隈の多くが既に所有）、実装が小さい、体感が良い。**3Dビューア的な用途とも噛み合う。**

既定マッピング案:

- 左スティック → 注視点を水平移動
- 右スティック → 旋回
- トリガー L/R → 距離のイン／アウト（アナログのため寄り引きの速度が指で出る）
- L1/R1 → 注視点の上下

### 実装で外せない2点

- **デッドゾーンは半径で取る。**軸ごとに切ると斜め入力で段差が出る
- **レスポンスカーブを入れる。**生のスティック値を速度にすると微調整が効かない。大きさを2乗〜3乗すると中心付近が繊細になる

この2つで操作感の質が大きく変わる。

### その他の注意

- **ユーザー操作があるまでゲームパッドが見えない。**Chromium はボタンが1回押されるまでゲームパッドを列挙しない。UI に「ボタンをどれか押してください」の案内が要る
- ポーリング方式のため、描画ループの中で毎フレーム `navigator.getGamepads()` を呼ぶ

## MIDI

Web MIDI API で完結する。

**本命はモーフのフェーダー操作。**安価なコントローラでもフェーダー8本＋ノブ8個があり、あ/い/う/え/お＋まばたき＋眉を割り当てられる。MIDI CC は 7bit（128段階）だが 0〜1 のモーフには十分で、**物理フェーダーの触感で微妙な半開きが出せる**ことが価値になる。

将来的には MIDI クロックを受けてタイムラインを外部テンポに同期できる可能性がある（BeatMap 構想と関連）。

### Electron での確認事項

- **権限。**`session.setPermissionRequestHandler` で `midi` の許可が必要になる可能性がある
- **sysex は要求しない。**不要であり、要求すると権限が重くなる
- **セキュアコンテキスト。**Web MIDI は secure context 前提。`file://` で読み込んでいると弾かれる可能性がある。実機での確認が要る

## Stream Deck

**ホットキー機能だけで需要の大半が満たされる。**Stream Deck の標準機能はキーの組み合わせをフォアグラウンドのアプリに送るだけであり、**MMD_modoki 側でショートカットが自由に登録できれば、連携実装ゼロで動く。**アイコンや名前は Stream Deck 側で自由に設定できる。

ダイヤル（Stream Deck +）については、**ダイヤルの回転を MIDI CC に変換するサードパーティのプラグインが存在する。**それを経由すれば MMD_modoki からは通常の MIDI コントローラとして見える。ただし利用者側に別途プラグインと仮想MIDIポートの用意が要るため、「Stream Deck 対応」と名乗るのではなく「**MIDI を出せるものなら何でも繋がる**」という位置づけになる。

残るのは「キーの表示にアプリの状態を出す」フィードバックのみ。**これ1つのために通信の口を開ける価値はない。**

## 通信の口を開けない方針

ショートカット、ゲームパッド、MIDI、Stream Deck（ホットキー）は**すべてブラウザAPIとキーイベントで完結する。**WebSocket などのローカルサーバは不要。

デスクトップアプリでローカルポートを開けることは、それ自体が攻撃面になる。**当面は開けない。**

将来どうしても必要になった場合のチェックリスト（覚え書き）:

- 既定 OFF、設定で明示的に有効化
- **可能なら WebSocket ではなく名前付きパイプ／Unixソケット。**ブラウザから物理的に触れなくなり、下2項目が不要になる
- WebSocket なら `Origin` と `Host` を検証する（ブラウザから localhost に繋がれる／DNSリバインディング対策）
- 起動時に生成したトークンを必須にする
- コマンドは列挙式にする。自由なパスや文字列評価を受け取らない
- bind 先は明示的に `127.0.0.1`

## リアルタイム収録（先の話）

DAW のように、再生しながら入力を動かしてキーとして記録する機能。

必要な部品の半分は既にある。

| 要るもの              | 状態                  |
| ----------------- | ------------------- |
| 実速度での再生           | ある                  |
| 連続値の入力            | Gamepad / Web MIDI  |
| 1テイク = 1 Command  | Command 基盤がある       |
| アーム（収録対象チャンネルの指定） | 無い                  |
| 平滑化とキー間引き         | 構想メモの Phase 3 に既にある |
| パンチイン／アウト         | 無い                  |

**カメラ追従ベイクと同じ土台である。**生の連続値を受け、平滑化し、間引き、キーに焼く。入力源がスティックかアルゴリズムかの違いしかない。したがって独立した機能として作るのではなく、追従ベイクの土台ができたときに入力源として繋ぐ形になる。

### 固有の課題: 遅延補正

人間は「見てから動かす」ため、入力をそのまま記録すると必ず後ろにズレる。ポーリング周期＋描画遅延＋人間の反応を見込んだオフセットが要る。**これだけは他の部品を流用できない。**

### 手前に安い版がある

Autokey が既にある。**収録の仕組みが1つも要らない。**

リアルタイムが要るのは「演奏として一発録りしたい」ときだけである。

## テスト方針

入力ソースを `navigator` 直叩きにせず、間にインターフェースを1枚挟む。

```other
入力ソース（実機 / テスト用の偽物）
  → 正規化した値
    → マッピング
      → コマンド or 連続値
```

こうすると**現物が無くてもマッピングのロジックをテストできる。**ハードウェアが手元に無い MIDI と Stream Deck でも、検証範囲を確保できる。

## やらないこと

- **通信の口（WebSocket / ローカルサーバ）。**上記のとおり不要
- **Stream Deck 専用プラグイン。**別配布物となり保守対象が増える。需要が確認できてから
- **振動（ハプティクス）。**Gamepad API に API はあるが対応がばらつき、動画編集ツールで震える必然性が薄い
- `mapping` **が `""` のマイナーなゲームパッドへの個別対応**
- **キーバインドをプロジェクトファイルに保存すること。**アプリの好みであり作品の設定ではない

## 段階

1. **現状の永続データ棚卸し**（localStorage に何があるか。クォータ不要）
2. **アプリ設定の保存方式を決めて実装**（保存場所判定、settings/state 分離、アトミック書き込み）
3. **自動バックアップ**（2の上に乗る）
4. **ショートカットキー登録**（コマンドID の整理を伴う。2の上に乗る）
5. **ゲームパッドでビューポート操作**（土台不要、実機あり）
6. **収録の仕組み**（追従ベイクと共通土台）
7. **MIDI**、**ゲームパッドでの収録**（ハード確認が要る）

2 と 4 は Codex 復帰前に設計を固められる。
