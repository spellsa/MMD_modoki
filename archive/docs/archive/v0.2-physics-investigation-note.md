# v0.2 物理演算・高負荷モデル調査メモ

更新日: 2026-04-27

## 目的

v0.2 では、Babylon.js 9.2.0 + babylon-mmd 1.2.0 を前提に、重めモデルでも扱いやすい物理演算へ寄せる。

このメモでは、v0.2 で調査・実装判断する物理まわりと高負荷 MMD モデル対応の項目を整理する。実装手順の詳細は既存の [physics-worker-implementation-plan.md](./physics-worker-implementation-plan.md) を参照する。

基本方針として、物理、マルチスレッド、GPU skinning / SDEF、高ポリゴンモデル読み込みは babylon-mmd の推奨する実装経路を素直に採用する。
MMD_modoki 側に残っている旧バージョン向けの回避コードや独自調整は、v0.2 の更新では維持を前提にしない。
必要なものだけを新しい経路へ移植し、古い実装は破棄してよい。
MMD_modoki 側で新たに足す責務は、主に Electron / Vite / packaged build 上で babylon-mmd の推奨経路が動くようにする統合部分とする。

## 優先順位

1. `MmdWasmInstanceTypeMPR` / Worker 物理の導入可否
2. `PhysicsRuntimeEvaluationType.Buffered` の採用可否
3. GPU skinning / SDEF / 多ポリゴンモデル読み込みの推奨経路確認
4. MPR 失敗時の SPR fallback
5. 重めモデル / 複数モデルでの FPS と physics time 比較
6. seek / Home / End / 再生開始 / ボーン編集後の安定性
7. 物理 backend 表示と performance log

## 現行前提

- 現在は babylon-mmd の Bullet WASM 物理を主経路にしている。
- Bullet 失敗時は Ammo.js へ fallback する。
- 物理 ON / OFF、重力、fixed step、substep は既に扱っている。
- `disableOffsetForConstraintFrame: true` は維持する。
- v0.2 で babylon-mmd は `1.2.0`、Babylon.js は `9.2.0` に更新済み。

ただし、これらの現行実装は v0.1 系向けに作った安定化コードを含む。
v0.2 では、現行コードの延命より babylon-mmd 1.2.0 の推奨経路へ寄せることを優先する。

## 採用条件

MPR / Buffered / GPU skinning 推奨経路を v0.2 標準候補にする条件:

- WebGPU 起動と同時に安定して初期化できる
- packaged build でも Worker / WASM / shader asset の解決が壊れない
- MPR 失敗時に SPR または Ammo へ自然に fallback できる
- SDEF / GPU skinning が babylon-mmd 推奨経路で動く
- 重めモデルで FPS または UI 応答性に明確な改善がある
- seek / pause / resume / Home / End 後に破綻しない
- 物理 OFF / backend 切替時に既存プロジェクトの読み込みを壊さない

見送り条件:

- COOP / COEP 対応が既存のローカルファイル読み込みを壊す
- Worker / WASM / shader asset の packaged build 解決が不安定
- Buffered で操作後の姿勢同期が目立って遅れる
- babylon-mmd 推奨経路から外れた独自実装が増えすぎる
- SPR と比べて改善が小さい一方で、実装・保守コストが大きい

## 実装方針メモ

- 最初は設定画面や詳細 UI へ広げず、内部切替 + debug 表示で検証する。
- babylon-mmd 1.2.0 の推奨実装を第一候補にし、v0.1 系向けの古い回避コードは必要なら破棄する。
- MMD_modoki 側の実装は Electron / Vite / packaged build 統合と、UI 表示・ログ・fallback に寄せる。
- MPR を入れても SPR を消さない。SPR は fallback と比較基準として残す。
- Ammo fallback は互換退避経路として残すが、v0.2 の主評価対象は Bullet SPR / Bullet MPR にする。
- 現行の Bullet / Ammo 初期化コードを流用する場合も、推奨経路との差分が説明できる範囲に留める。
- GPU skinning / SDEF は babylon-mmd 側の機能を使い、独自 shader 差し込みはできるだけ減らす。
- 通常再生と編集操作では最適な評価モードが違う可能性があるため、最初から固定せず比較する。
- 物理 performance log は SQLite 実験とは混ぜず、まずメモリ内集計または console/debug 表示に留める。

## 実装プラン

### Phase 1: 現行差分の整理

対象:

- `src/mmd-manager.ts`
- `src/assets/model-asset-service.ts`

確認する現行差分:

- 現在は `spr` wasm を直接 import し、独自の `loadSprWasmInstance()` 経由で初期化している
- backend 表示は `bullet | ammo | none` で、SPR / MPR の区別がない
- `SdefInjector.OverrideEngineCreateEffect(engine)` は既に呼んでいる
- WebGPU SDEF mesh を CPU skinning に落とす独自 fallback が残っている
- 高ボーン数 skeleton を CPU skinning に落とす独自 fallback がある

方針:

- babylon-mmd 1.2.0 推奨の `GetMmdWasmInstance(new MmdWasmInstanceTypeMPR())` / `MultiPhysicsRuntime` / `MmdBulletPhysics` を基準にする
- v0.1 系向けの回避コードは、推奨経路と衝突する場合は破棄する
- GPU / Electron 制約のために必要な fallback は、理由を明確にして残す

### Phase 2: backend 種別の細分化

`physicsBackend` を次の粒度へ変更する:

```ts
"none" | "bullet-spr" | "bullet-mpr" | "ammo"
```

対応する表示:

- `Bullet MPR`
- `Bullet SPR`
- `Ammo`
- `Off`

更新対象:

- backend badge
- `getPhysicsBackendLabel()`
- smoke log
- diagnostics / console log
- fallback warning

fallback 経路は `MPR -> SPR -> Ammo -> none` として記録する。

### Phase 3: MPR 初期化を主経路にする

初期化順:

1. MPR 利用可否を判定する
   - `SharedArrayBuffer`
   - `crossOriginIsolated`
   - COOP / COEP
   - Worker helper / WASM asset の URL 解決
2. MPR 初期化を試す
3. MPR 失敗時は SPR へ fallback
4. SPR 失敗時は Ammo へ fallback
5. Ammo 失敗時は physics off

`MultiPhysicsRuntime` は MPR / SPR の共通経路として使い、MMD runtime 側には `MmdBulletPhysics(runtime)` を接続する。

MMD_modoki 側では、Worker や WASM の中身を再実装しない。必要なのは Electron / Vite / packaged build で babylon-mmd の推奨経路が成立するようにする統合部分に限定する。

実装時の補足:

- MPR は `GetMmdWasmInstance(new MmdWasmInstanceTypeMPR())` を主経路にする
- SPR は Vite / Electron dev 環境で babylon-mmd 標準の URL 解決が HTML に落ちるケースがあるため、当面は明示的に `spr/index_bg.wasm?url` を渡す fallback 経路を維持する
- SPR の明示 URL 経路は、babylon-mmd の wasm / typed array API を使う統合コードとして扱い、Worker / 物理実装そのものは再実装しない

### Phase 4: Buffered 評価の段階導入

MPR 起動が安定してから、`PhysicsRuntimeEvaluationType.Buffered` を試す。

初期方針:

- 通常再生: Buffered 候補
- seek / Home / End 直後: Immediate 候補
- ボーンギズモ操作中・直後: Immediate 候補
- pause 中の手動編集: Immediate 候補

Buffered は性能改善が出ても、操作直後の姿勢同期が悪ければ標準にしない。

### Phase 5: CPU fallback の棚卸し

`applyCpuSkinningFallbackForWebGpuSdefMeshes()` は Babylon 8 時代の WebGPU / SDEF 回避実装の可能性がある。
v0.2 では、babylon-mmd 1.2.0 + Babylon.js 9.2.0 の推奨 SDEF / WGSL 経路で再確認し、不要なら削除候補にする。

一方、高ボーン数で GPU bone texture の上限を超える fallback は、Babylon / GPU 制約への退避として残す可能性がある。

分類:

- 推奨経路と衝突する旧回避コード: 破棄候補
- GPU / Electron / packaged build 制約の退避: 条件付きで維持
- 原因が不明なまま残っている fallback: 調査して削除または明文化

### Phase 6: 計測

最初は大きな UI を作らず、console / diagnostics / 簡易 debug 表示で確認する。

測るもの:

- engine: WebGPU / WebGL2
- backend: Bullet MPR / Bullet SPR / Ammo / Off
- evaluation: Immediate / Buffered
- model count
- FPS
- physics step time
- fallback reason
- CPU skinning fallback の有無

### 最初の実装単位

最初の差分は、物理初期化と表示に閉じる。

1. `physicsBackend` を `bullet-spr` / `bullet-mpr` に細分化する
2. MPR 可否判定 helper を追加する
3. MPR 初期化を主経路に追加する
4. MPR 失敗時 SPR fallback を実装する
5. UI / log / smoke の backend 表示を更新する
6. WebGPU SDEF CPU fallback を feature flag 的に切れる形へ変更する
7. `npm.cmd run lint`
8. `npm.cmd run smoke:launch`

Buffered 評価と CPU fallback 削除は、MPR 起動確認後に別差分で扱う。

### 2026-04-27 WebGPU SDEF CPU fallback の扱い

実装方針:

- Babylon.js 9.2.0 + babylon-mmd 1.2.0 では、まず babylon-mmd 側の SDEF / WGSL 経路を優先する
- v0.1 系の WebGPU SDEF CPU fallback は既定で無効化し、必要な場合だけ戻せる実験フラグにする
- 高ボーン数 skeleton の CPU fallback は Babylon.js 9 の 2D bone matrix texture 経路と衝突するため削除する

実装済み:

- `applyCpuSkinningFallbackForWebGpuSdefMeshes()` は `mmd_modoki.webGpuSdefCpuFallback` が有効な場合だけ実行する
- 既定値は `false`
- 必要な場合は DevTools 等から `localStorage.setItem("mmd_modoki.webGpuSdefCpuFallback", "1")` で旧 fallback を有効化できる
- import 前の高ボーン数 CPU skinning fallback observer を削除した
- import 後の oversized skeleton CPU skinning fallback を削除した
- `(bones + 1) * 4 > maxTextureSize` の場合は、Babylon.js 9 の 2D bone matrix texture に任せる
- 高ボーン数 skeleton では `GPU bone texture: ...` diagnostic を残す

次に確認すること:

- 4274 ボーン級モデルで `Early CPU skinning fallback armed before import` が出ないこと
- 同モデルで `GPU bone texture: ...` が出て GPU skinning が維持されること
- SDEF / position morph を含むモデルで WebGPU 表示が破綻しないか確認する
- 破綻するモデルがある場合だけ、fallback 条件をモデル単位または mesh 単位で再設計する
- 問題が出なければ、この fallback は削除候補にする

確認結果:

- 4274 ボーン級モデルで `Early CPU skinning fallback armed before import` は出なくなった
- 同モデルで `GPU bone texture storage enabled for large skeleton` が出た
- bone matrix texture は `8192x3` として確保された
- CPU fallback 時に出ていたモーフによる顔崩れが改善した
- 動画出力でも物理演算は動作した
- FPS は CPU fallback 時も GPU bone texture 時も 1fps 程度で、対象モデルが重すぎるため性能差は判断不能
- 中規模モデル 4 体のプロジェクトでは、体感で 5〜10fps 程度の改善が見えた

- COEP 付与後に PMX texture、音声、ローカル隣接ファイル解決が壊れないか、実データで確認する
- 現時点の package 版は `MPR packaged build integration is pending` として SPR fallback する設計にしている

### 2026-04-27 Buffered 評価の初期導入

実装済み:

- babylon-mmd の `PhysicsRuntimeEvaluationType` を使い、`MultiPhysicsRuntime.evaluationType` を切り替える経路を追加した
- MPR + 通常再生 + 物理有効時に `Buffered` へ切り替える実験を行った
- 実モデル複数体の再生中に、物理剛体がボーンへ追従せず髪や剛体付きパーツが崩れる現象が出た
- 2026-04-27 時点では再生中も `Immediate` 固定へ戻した
- 10 秒ごとの物理ログに `evaluationType` を含める

方針:

- Buffered は物理を別 worker 側へ逃がせる可能性がある一方、seek や手動編集では 1 フレーム遅れや同期ズレが見えやすい
- 現時点では、MMD_modoki の複数モデル再生 / 手動 seek / 既存の `afterPhysics` patch と衝突している可能性が高い
- v0.2 初期実装では `Immediate` を標準にし、Buffered は別途検証が終わるまで標準経路に入れない
- SPR fallback と package 版では、現時点では Immediate 中心で扱う

確認結果:

- `npm.cmd run lint`: 成功。既存 warning のみ
- `npm.cmd run smoke:launch`: 成功。`engine=WebGPU`, `physics=Bullet MPR`, `crossOriginIsolated=true`

## 2026-07-09 追記: babylon-mmd 公式 MPR 経路の再確認

確認元:

- https://noname0310.github.io/babylon-mmd/ja/docs/reference/runtime/apply-physics-to-mmd-models/
- https://noname0310.github.io/babylon-mmd/ja/docs/reference/runtime/bullet-physics/
- https://noname0310.github.io/babylon-mmd/ja/docs/get-started/add-physics/
- https://noname0310.github.io/babylon-mmd/ja/docs/reference/runtime/mmd-webassembly-runtime/
- `node_modules/babylon-mmd/esm/Runtime/Optimized/mmdWasmInstance.js`
- `node_modules/babylon-mmd/esm/Runtime/Optimized/InstanceType/multiPhysicsRelease.js`
- `node_modules/babylon-mmd/esm/Runtime/Optimized/Physics/Bind/Impl/multiPhysicsRuntime.js`

公式推奨の Classic runtime + Bullet MPR 経路:

```ts
const wasmInstance = await GetMmdWasmInstance(new MmdWasmInstanceTypeMPR());
const physicsRuntime = new MultiPhysicsRuntime(wasmInstance);
physicsRuntime.setGravity(new Vector3(0, -98, 0));
physicsRuntime.register(scene);
const mmdRuntime = new MmdRuntime(scene, new MmdBulletPhysics(physicsRuntime));
```

MPR の要件:

- `WebAssembly`
- `SharedArrayBuffer`
- secure context 相当
- `Cross-Origin-Opener-Policy: same-origin`
- `Cross-Origin-Embedder-Policy: require-corp`

`node_modules` の `MmdWasmInstanceTypeMPR` コメントにも同じ要件が書かれている。現行 dev smoke の `crossOriginIsolated=true` / `sharedArrayBufferAvailable=true` はこの条件確認として妥当。

重要な読み替え:

- `MmdWasmInstanceTypeMPR` は「multi-threaded physics release の wasm instance」を選ぶもの。
- `MultiPhysicsRuntime` の既定 `evaluationType` は `Immediate`。
- 公式 Bullet Physics ページでは、`PhysicsRuntime` / `MultiPhysicsRuntime` の `evaluationType = PhysicsRuntimeEvaluationType.Buffered` のとき、マルチスレッド可能な環境では別 worker thread で物理シミュレーションを処理すると説明されている。
- つまり、現行の `MPR + Immediate` は MPR wasm を使っているが、物理 step 自体は `afterAnimations()` 内の immediate step が中心。並列化の主効果を確認するには `Buffered` 再検証が必要。
- ただし v0.2 の実機検証では、`Buffered` で剛体がボーンへ追従せず崩れる症状を確認済みのため、標準復帰は急がない。

現行実装との差分:

- MMD_modoki は公式の `GetMmdWasmInstance(new MmdWasmInstanceTypeMPR())` を直接使わず、`src/mmd-manager.ts` の `loadBundledMprWasmInstance()` で wasm-bindgen module と `index_bg.wasm?url` を明示して初期化している。
- 理由は既存メモどおり、Vite / Electron dev で標準 loader の wasm URL 解決が HTML へずれるケースと、packaged build の Rollup / worker helper 統合未整理を避けるため。
- この回避経路でも、実体としては `MultiPhysicsRuntime(wasmInstance)` に渡せる `IMmdWasmInstance` を作っており、公式の Classic runtime + `MmdBulletPhysics(MultiPhysicsRuntime)` 構成とは大筋で一致している。
- `MmdWasmRuntime + MmdWasmPhysics` は公式上も別経路。JS binding layer を減らせるが、MMD_modoki の editor runtime bone 参照、timeline、project save/load への影響があるため、現行安定版とは分けて扱う。

Classic / WASM runtime の違い:

- Classic runtime でも物理本体は Bullet WASM。`Classic` は「物理が WASM ではない」という意味ではなく、MMD runtime 本体に `MmdRuntime` を使うという意味。
- Classic runtime は `MmdRuntime` を使う標準経路。MMD runtime 本体は JS 側に置き、物理は `MmdBulletPhysics` + `MultiPhysicsRuntime` 経由で Bullet WASM へ接続する。
- Classic runtime の `Bullet MPR` / `Bullet SPR` は、物理用 Bullet wasm instance の種類を指す。
  - `MPR`: `MmdWasmInstanceTypeMPR` 相当。multi-threaded / physics / release build。
  - `SPR`: `MmdWasmInstanceTypeSPR` 相当。single-threaded / physics / release build。
- `MmdWasmPhysics` は `MmdWasmRuntime` 用の physics adapter。WASM 物理を使うためのものではあるが、Classic runtime の `MmdRuntime` に差し替えて使うものではない。
- WASM runtime は `MmdWasmRuntime` + `MmdWasmPhysics` を使う実験経路。これは「Classic runtime の物理 backend を MPR にするだけ」ではなく、runtime 全体の差し替えとして扱う。
- v0.2 の性能比較では、まず Classic runtime + Bullet MPR / SPR を基準にする。UI badge や smoke log が `WASM MPR` になっている場合は、WASM runtime PoC で測っている可能性があるため、Classic と同じ土俵の物理 backend 比較として読まない。
- `localStorage["mmd_modoki.runtimeMode"] === "wasm"` の状態では WASM runtime 経路になる。Classic 基準で再測定する場合は UI の `Runtime: Classic` へ戻すか、`localStorage.setItem("mmd_modoki.runtimeMode", "classic")` 後に reload する。

次に見るべき点:

1. `MPR + Immediate` と `SPR + Immediate` の実モデル比較を続ける。ここで差が小さい場合、MPR loader より描画・skinning・overlay 側が支配的な可能性が高い。
2. `Buffered` 再調査は、単体モデル、複数モデル、`patchModelAfterPhysicsForPausedState()` 無効化、manual playback 無効化を分ける。
3. `MultiPhysicsRuntime` constructor の `preserveBackBuffer` option は、Buffered から Immediate へ戻すときの motion state buffer 同期に関係する可能性がある。WebM snapshot 復元や Buffered 崩れの調査候補にする。
4. packaged MPR 対応は、公式 `GetMmdWasmInstance` に戻せるか、現行の明示 wasm URL 方式を維持して worker helper を同梱するかを比較する。

## 2026-07-09 追記: 現行物理パラメータ洗い出し

MMD_modoki 側で明示している値:

| 項目 | 現行値 | 実装箇所 |
| --- | --- | --- |
| simulation rate | `60Hz` 固定 | `PhysicsRuntimeController.simulationRateHz` |
| fixed time step | `1 / 60` | `PhysicsRuntimeController.applySimulationRate()` |
| max sub steps | `2` | `PhysicsRuntimeController.applySimulationRate()` |
| gravity acceleration | 既定 `98` | `PhysicsRuntimeController.gravityAcceleration` |
| gravity direction | 既定 `(0, -100, 0)` を normalize して `(0, -1, 0)` | `PhysicsRuntimeController.gravityDirection` |
| evaluation type | 再生中の Bullet MPR は `Buffered`、停止 / seek / Bullet SPR は `Immediate` | `syncBulletEvaluationTypeForPlayback()` / `syncBulletEvaluationTypeForSeek()` |
| buildPhysics option | `{ disableOffsetForConstraintFrame: true }` | `model-asset-service.ts` |

substep の読み方:

- `maxSubSteps = 180` は「1 frame あたり最大何 substep まで許すか」の上限。
- 通常 60fps / 60Hz では実 substep は概ね 1。
- frame drop 時は最大 180 step まで catch-up を許す。描画は飛ばしても物理は 60Hz substep で追いつかせる。

MMD_modoki 側で明示していない値:

- solver iteration 数。
  - Bullet WASM binding 側も MMD_modoki から iteration 数を渡していない。
  - 現行の Bullet MPR / SPR wasm binding には、確認範囲では `getSolverInfo` / `setNumIterations` 相当の public export がない。
  - 古い調査メモの `numIterations = 10` は候補値 / 既定推定として扱い、現行 Bullet MPR / SPR 実測値ではない。
  - 正攻法で設定するには babylon-mmd / Bullet wasm binding 側に solver info API を追加する必要がある。

MMD_modoki 側で MMD joint constraint に後段適用する値:

- ERP / stop ERP: `0.475`。
  - `ConstraintERP` / `ConstraintStopERP` を 6 軸へ設定する。
  - babylon-mmd 標準の stop ERP `0.475` に戻した。`0.25` は若干変化したが、布の垂れ解消には不足した。
- CFM / stop CFM: `0`。
  - `ConstraintCFM` / `ConstraintStopCFM` を 6 軸へ設定する。
  - `0.25` は Classic Bullet で布や袖が垂れる主因と見られる。`0` に戻すと改善が大きかった。
  - babylon-mmd 標準の MMD joint 生成処理では CFM 系 param への `setParam` 呼び出しは見当たらないため、MMD_modoki 側で柔らかさを追加してしまっていた可能性が高い。
- 適用箇所:
  - `PhysicsModelController.applyMmdConstraintSolverParameters()`
  - Bullet MPR / SPR は `_physicsModel._constraints`。

次の確認候補:

- `physics performance sample` の `physicsFixedTimeStepMs`, `physicsMaxSubSteps`, `physicsDeltaRawMaxMs`, `physicsDeltaUsedMaxMs` を見る。
- Bullet の solver iteration を public binding から読めないため、upstream API 追加または wasm binding patch が必要か判断する。
- ERP `0.475` / CFM `0` を基準値として、長髪・スカート・袖モデルの挙動差を確認する。

### 2026-07-10 Classic Bullet 布垂れ切り分け

症状:

- Classic runtime + Bullet MPR で、特定モデルの布・袖・スカートが WASM runtime より垂れる。
- 再生中だけでなく停止時にも同じ傾向が見えるため、`Buffered` 固有の評価遅延では説明しにくい。
- Classic Buffered は速度面では最も有望なので、布垂れを直して実用候補に戻したい。

試したこと:

- `Generic6DofSpringConstraint#setStiffness` の補正値を UI から触れる実験をしたが、主因ではなさそうだったため撤去した。
- `Buffered` / `Immediate` を比較したが、停止時にも垂れが出るため主犯候補から外した。
- ERP / StopERP を `0.25` から babylon-mmd 標準寄りの `0.475` に戻した。若干変化はあったが、まだ垂れた。
- CFM / StopCFM を `0.25` から `0` に戻したところ、布垂れが大きく改善した。

結論:

- Classic Bullet の布垂れは CFM / StopCFM `0.25` が主因だった可能性が高い。
- CFM は constraint の柔らかさを増やす方向に効くため、MMD 向けの joint に一律 `0.25` を入れると、布・袖・スカートの拘束が緩くなりすぎる。
- 現時点の基準値は ERP / StopERP `0.475`、CFM / StopCFM `0`。
- Buffered は速度改善効果が大きく、今回の垂れ原因からはほぼ釈放。引き続き Classic Bullet MPR + Buffered を実用候補として検証する。
- 長髪破綻モデルでは frame skip 時の 60Hz substep catch-up と `physicsStepMaxMs` を確認する。

### 2026-07-10 追記: 再生中の物理 OFF/ON 復帰

現象:

- 再生中にメニューバーから物理演算を OFF にするところまでは正常。
- そのまま ON に戻すと、モデルのアニメーションは進むが、物理だけ OFF 直前付近の位置に残ることがあった。
- 物理 OFF とは異なり、剛体状態だけが古い Buffered / Bullet 側 state を参照しているような挙動だった。

原因候補:

- OFF 中も MMD animation は進むが、Bullet 側の剛体姿勢・速度・Buffered motion state は現在ボーン姿勢へ十分に同期されない。
- ON 復帰時に最初から Buffered へ戻すと、worker / buffer 側に残った古い state を参照し、物理が現在フレームへ復帰しないことがある。

対応:

- グローバル物理を OFF -> ON に戻す瞬間だけ、再生中でも一度 `Immediate` として有効化する。
- ON 復帰時に、各モデルの physics model を現在ポーズへ即時リセットする。
  - `initializePhysics()` を呼び、現在ボーン姿勢から rigid body transform を再構築する。
  - `commitBodyStates()` で `rigidBodyStates` を反映する。
  - rigid body / bundle の線形速度・角速度を 0 にする。
  - Buffered 経路では `commitToWasm()` と `updateBufferedMotionStates(true)` で内部 buffer も同期する。
- リセット後、再生中かつ Buffered が有効なら `syncBulletEvaluationTypeForPlayback(true)` で Buffered に戻す。

仕様:

- 物理 ON 復帰時は `Immediate -> pose reset -> Buffered復帰` の順序を必ず守る。
- この順序を崩すと、Classic Bullet MPR + Buffered で物理だけ置き去りになる可能性がある。

## 2026-07-09 追記: frame skip と 60Hz 固定物理 step

重いモデルで貫通が出る場合、solver iteration 未設定そのものよりも frame skip 後の catch-up step が破綻を誘発している可能性がある。

確認した経路:

- Classic Bullet MPR / SPR の `MultiPhysicsRuntime.register(scene)` は `scene.onAfterAnimationsObservable` から `scene.getEngine().getDeltaTime()` を `afterAnimations()` に渡す。
- `afterAnimations()` 内では Babylon.js の `Scene.MinDeltaTime` / `Scene.MaxDeltaTime` で clamp してから `stepSimulation(delta, maxSubSteps, fixedTimeStep)` を呼ぶ。
- Babylon.js の既定 `Scene.MaxDeltaTime` は `1000ms`。MMD_modoki では物理詰まりを消化しやすくしつつ UI フリーズに見えにくい上限として `3000ms` へ広げる。
- MMD_modoki の render loop 側にも `100ms` clamp はあるが、これは手動再生や motion blur 側の delta であり、babylon-mmd 物理 runtime に渡る delta とは別経路。
- WASM runtime 実験経路も `PhysicsClock` が `engine.getDeltaTime() / 1000` を返すため、同じ種類の frame skip 影響を受ける。

実装した対策:

- MMD 本体寄せとして physics simulation rate を `60Hz` 固定にする。
- `fixedTimeStep = 1 / 60` に固定する。
- `maxSubSteps = 180` に固定し、描画 frame が落ちた場合も最大 3 秒分を 60Hz substep として消化できるようにする。
- 3 秒を超える詰まりや、物理 step 自体が実時間より遅い重量モデルでは追いつきを保証しない。上限を大きくしすぎると UI が止まって見えるため、現時点ではフリーズ回避と物理復元の妥協点として 3 秒に留める。
- Classic Bullet MPR / SPR は `PhysicsRuntimeController.installBulletStepTiming()` で `MultiPhysicsRuntime.afterAnimations(deltaTime)` に渡る delta を記録し、そのまま runtime へ渡す。
- WASM runtime 実験経路は `MmdWasmRuntime` の private `_physicsClock` を wrap し、`getDeltaTime()` の戻り値を記録したうえでそのまま返す。
- performance log に以下を追加する:
  - `physicsFixedTimeStepMs`
  - `physicsMaxSubSteps`
  - `physicsDeltaSamples`
  - `physicsDeltaRawMaxMs`
  - `physicsDeltaUsedMaxMs`
  - `physicsDeltaLastRawMs`
  - `physicsDeltaLastUsedMs`

Buffered 再試行:

- 2026-07-09 時点で、Classic runtime + Bullet MPR + 再生中だけ `PhysicsRuntimeEvaluationType.Buffered` を再試行する。
- `Buffered + maxSubSteps = 180` で、体だけ先に進んで布や髪が追いつかない問題が改善するかを見る。
- pause / stop / seek では `Immediate` に戻し、編集・停止中の同期崩れを避ける。
- Bullet SPR と WASM runtime 実験経路では `Immediate` のまま扱う。
- 以前の検証では `Buffered` で剛体がボーンへ追従せず崩れたため、FPS 改善だけでなく長髪 / スカート / 袖の追従崩れを同時に見る。
- 実機確認では、`Buffered + maxSubSteps = 1` で通常 60fps 付近まで改善し、`Buffered + maxSubSteps = 2` でも通常 55fps 前後、影なし 60fps まで出た。MMD 本体にかなり近い速度まで改善している。
- 速度面では `Buffered` を標準候補にしつつ、物理品質優先で `maxSubSteps = 180` にする。残る判断軸は物理品質、seek / pause / resume / 編集直後の同期崩れ。

読み方:

- `physicsDeltaRawMaxMs` が大きく、`physicsDeltaUsedMaxMs` も同じ値なら、物理時間は捨てずに Bullet 側の fixed timestep 経路へ渡している。
- `physicsStepMaxMs` が大きくなる場合、その区間で複数 substep の catch-up が走っている可能性が高い。
- 14fps 程度まで落ちた時点では 1 frame あたり 4〜5 step を試みる。負荷は増えるが、体モーションと物理の時間ずれを避けるための標準値とする。
- これでも残る場合は、剛体形状、joint limit / spring、MMD 本家との差、solver iteration API 追加の順で見る。

FPS 固定モード:

- 2026-07-12 に表示メニューへ `fps無制限` / `60fps制限` / `30fps制限` を追加した。
- 既定は本家 MMD 寄せで `60fps制限`。
- `1fpsセーフモード` と `boneCount > 4095` 自動切替も試したが、物理の置いていかれが目立ち、効果が微妙だったため没にした。GPU bone texture storage の診断ログは残すが、FPS 自動切替には使わない。

## 2026-07-09 追記: Ammo fallback を標準経路から外す

方針:

- 物理 backend は Bullet 系へ揃える。
- Classic runtime の選択肢は `MmdWasmInstanceTypeMPR` 相当と `MmdWasmInstanceTypeSPR` 相当の 2 本にする。
- `MPR`: multi-threaded / physics / release build。dev で `SharedArrayBuffer` と cross-origin isolation が成立する場合の優先経路。
- `SPR`: single-threaded / physics / release build。MPR が使えない場合の fallback。
- Bullet MPR / SPR の両方が初期化できない場合は Ammo へ落とさず、物理 Off で起動を継続する。

理由:

- MMD 寄せの ERP / CFM `0.25` や `disableOffsetForConstraintFrame` の検証対象を Bullet に集約する。
- fallback 差による挙動差を減らし、長髪・スカート・袖などの破綻比較を `MPR / SPR / Off` へ絞る。
- Ammo.js は Bullet の Emscripten port だが、現行の主経路ではなくなったため標準 fallback から外す。
